# Playback correctness PR follow-up review

Reviewed candidate: PR #33 at `59d0ed17dcccdb976e3302c0ba29a70c27efd10b`.
This note records the additional JPEG guard, AAC metadata fix and MOV control
added during review.

## JPEG component arrangement

The parser previously limited each sampling factor to 1 or 2 and the total MCU
block count to six. This protected `m_MCUIdx`, but also admitted layouts with
multiple Cb or Cr blocks. Maximum MCU width/height alone do not distinguish
these layouts from the decoder's supported Y/Cb/Cr arrangements.

The native path selects one of four CSC microprograms solely from MCU dimensions
(`_init_clr_fmt`). The scratchpad DMA packets contain block coefficients and
fixed VIF commands; `_process_MCU` submits the blocks in component order.
`m_HDIV`/`m_VDIV` are computed on the CPU but are never transferred or consumed
by that path. The selected microprogram therefore receives no metadata that
could describe moving the additional blocks from Y to Cb/Cr. Reject these
arrangements before rescaler allocation or color-program dispatch. Retain the
four supported layouts: Y sampling 1×1, 2×1, 1×2 or 2×2, each with Cb/Cr 1×1.

Four added controls fit the old six-block bound but put extra blocks in chroma.
The rejection assertion failed at the original head. The fixed parser rejects
them while retaining the canonical synthetic layouts, independent FFmpeg JPEG
controls and bundled-image controls. These host controls exercise parser and
entropy code with VU/rescaler adapters; they do not certify console pixels or
DMA scheduling. An otherwise valid JPEG in an unsupported arrangement now fails
to load instead of being dispatched through an incompatible native layout.
FFmpeg 5.1.9 also emits 4:4:4 JPEGs with sampling 1×2 on all three components;
these now fail safely. This is a supported-layout restriction, even though the
file is valid JPEG. The independent-encoder controls report the actual sampling
and expected acceptance instead of assuming that every encoder version emits
the same arrangement for a given pixel format.

## Unowned MOV edit list

An `elst` before the first track was investigated as a possible unpublished
stream access. The existing `_mov_read_dflt` stream-child guard already skips
that atom safely. No production MOV change was needed. The added fixture keeps
the atom well formed and verifies that all resulting packet offsets, sizes,
PTS and DTS still match FFprobe. It is an accepted-input control, not a claim
that the reporter's full-player late-start/stall has been reproduced or fixed.

## AAC metadata channel count

The complete host gate on FFmpeg 5.1.9 found that the existing M4A metadata
control returned stereo for a mono AAC-LC track. The sample entry reports two
channels, while AudioSpecificConfig and FFprobe report one. The playback
decoder already reads AudioSpecificConfig; the lightweight metadata path
previously skipped it. Read the two-byte indexed-rate AAC-LC configuration
within the atom's remaining bytes and use its rate/channel configuration.
Keep the existing sample-entry fallback for PCE, explicit frequencies and other
object types. This changes metadata only, not the AAC decoder or playback.

Mono and stereo fixtures now compare metadata against independent FFprobe
stream results and verify that the probe returns the file position to zero.
The mono control failed before the fix with rate 8000, channels 2 and a restored
position; it passes with channel count 1 after the fix.
An overstated AudioSpecificConfig length also has a full-file rejection control.
The probe now uses the metadata table's parser result directly: the full-player
header helper previously converted parser errors to zero, so testing that helper
for a nonnegative result could accept partially populated metadata on error.

## Artwork integration and the native GP window

The combined artwork branch exposed a native BDM link failure under the pinned
GCC 3.2.3 release flags (`-G8192 -mgpopt`). The new immutable 52-byte AAC rate
lookup was placed in `.sdata`, pushing common GUI globals beyond the signed
16-bit GP displacement window. The local failing map placed `_gp` at `0x2b5470`
and `g_pFileMenu` at `0x2bd484`, a displacement of `0x8014`.

Place only this new constant lookup in `.rodata`, following the existing source
section convention. The same BDM build then links and packs: `.sdata` shrinks
from `0x9706` to `0x96ce`, `.sbss` begins 128 bytes earlier after alignment, and
`g_pFileMenu` is at displacement `0x7f94`. Compiler version, release/diagnostic
GP thresholds, linker script, storage configuration and decoder behavior stay
the same. The existing native CI link gate remains necessary as this legacy
small-data region has little spare capacity.
