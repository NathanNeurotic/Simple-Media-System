# i25-shuffle-playlist

Issue #25 shuffle review (read-only; repo untouched, all scratch work under (investigator scratch, not kept)/i25-shuffle-playlist/). No PS2 hardware or emulator run was done.

FOUND (4): (1) HIGH - with Randomize on, any .m3u or Play all -> Audio folder containing two entries with the same display title hangs SMS forever (reproduced on host with the real SMS_GetContainerM3U; one-line fix verified). (2) LOW - shuffle seed is always a multiple of 8, which biases the production LCG's first draw (one track of 9 picked 15.4% vs 9.3%; 4-video orders 0.82x-1.23x); `g_Timer >> 3` at 3 sites removes it (verified). (3) LOW - continuous audio playback opens tracks with SMS_FA_FLAGS_AVI, so a same-named .srt/.sub/.txt is opened as a subtitle context that the audio-only player never closes (one-token fix verified at the call site). (4) LOW docs/comment - single-track continuation under Randomize is random-with-replacement and endless; code comment misdescribes it and the docs do not mention it.

All three code fixes plus the proposed test_m3u_probe.py case were applied to a private tree (.../i25-shuffle-playlist/tree): tools/test_m3u_probe.py, test_playlist_playback.py, test_playlist_menu.py pass (PASS=3 FAIL=0) and the pinned ee-gcc 3.2.3 build links cleanly (build/i25-shuffle.log, SMS.elf produced, no new warnings in the two files).

RULED OUT: 
- Same order every boot: no. Every shuffle reseeds g_RandSeed from g_Timer (125 Hz tick counter since SMS_TimerInit, written only in SMS_Timer.s), so the order depends on when the user triggers it.
- Fisher-Yates in _start_playlist (SMS_GUICmdProc.c:218-257): algorithm and prev/next/head/tail relinking are correct; scratch array is freed; malloc failure just skips the shuffle; no node is allocated/freed so RestoreFileDir's SMS_ListDestroy is safe. No double shuffle: Video goes only through _start_playlist, Audio/.m3u only through the M3U container.
- Subtitle pairing after shuffle: SMS_OpenMediaFile finds subs by name (SMS_ListFindI), not adjacency. A shuffled list whose head is a subtitle node gives lpSel==NULL, which GUIMenu_SelectItemByName handles (selects first item).
- LCG range/crash: SMS_rand can return negatives (confirmed from ee-gcc -S: mult/addu/div/mfhi), but all three shuffle sites reduce it as unsigned (divu), so no out-of-range index. Its real period is short (cycles of 80-6975; 802-80135 distinct draws before repeating over 6000 sampled seeds), which only matters for folders of ~800+ entries and still yields a valid permutation - not worth changing.
- Large folders: M3U shuffle is O(N^2) list walks, negligible at realistic sizes.
- Continuous-audio loop after Play all -> Audio/Images or a single video/picture/.m3u: exits immediately (m_Param is 0/GUICON_AVI/PICTURE/M3U, never GUICON_MP3=4).
- Repeat/stop: Repeat mode (audio only) keeps Play() from returning, so it never interacts with the shuffle loops; user stop ends both loops; video Play all plays the shuffled list once and returns to the browser (looping would be a new feature, not proposed).
- Docs do say where the toggle lives (Player settings -> MP3 settings -> Randomize playlist) in README.md, docs/settings.html, video.html, controls.html, known-issues.html and wiki.
- Existing tests: test_playlist_playback.py uses a toy RNG and test_m3u_probe.py stubs SMS_rand to 0 and never sets SMS_PF_RAND, so the M3U shuffle had zero coverage before the proposed case.

## #1 Randomize playlist hangs SMS forever when an .m3u or Play all -> Audio folder has two entries with the same title
- issue: 25
- severity: high
- category: bug
- files: ['src/SMS_ContainerM3U.c', 'tools/test_m3u_probe.py']
- reproduced: True
- confidence: 0.95
- risk: Very low. Removes a comparison only; list ownership, entry count and the non-shuffle path are unchanged. Behaviour differs only for inputs that previously hung.

### evidence
src/SMS_ContainerM3U.c:426-438 (shuffle loop, identical in upstream 2.9rev4):
  while ( lSize ) {
   unsigned int  lIdx   = SMS_rand () % lSize;
   SMS_ListNode* lpNode = SMS_ListAt ( lpList, lIdx );
   if (   !lpNode || SMS_ListFind (  lpNewList, _STR( lpNode )  )   ) continue;   /* line 431 */
   SMS_ListPushBack ( lpNewList, ... ); SMS_ListRemove ( lpList, lpNode ); --lSize;
  }
The SMS_ListFind test compares TITLES. Once a title is in lpNewList, any remaining node with the same title can never be moved, lSize never reaches 0, and the loop spins forever (console must be reset). Titles collide easily: (a) Play all -> Audio builds titles by stripping the extension (lines 313-315), so song.mp3 + song.flac in one folder collide; (b) .m3u entries without #EXTINF use the basename (line 390), so CD1/01.mp3 + CD2/01.mp3 collide; (c) the same file listed twice; (d) identical #EXTINF titles. Issue #25's closing comment advertises exactly this path (Play all -> Audio with Randomize).

REPRODUCED on host with the real SMS_GetContainerM3U, real SMS_List helpers and the production LCG (scratch harness .../i25-shuffle-playlist/m3u_shuffle.py, built from tools/test_m3u_probe.py). Output on current source:
  seed=8000 unique 5 tracks: rc=0 order=[c][b][e][d][a]
  seed=8000 multi-disc, same basename (CD1/01.mp3 + CD2/01.mp3): HANG (no return after 10 s, 100% CPU)
  seed=8000 same file listed twice: HANG
  seed=8000 EXTINF identical titles: HANG
  PLAY-ALL-AUDIO shuffle=ON folder song.mp3 + song.flac: HANG
  PLAY-ALL-AUDIO shuffle=OFF folder song.mp3 + song.flac: rc=0 (plays both)
Same results with seed 123456. With the one-line fix every case returns rc=0 with all entries present, also under ASan+UBSan, and the stock tools/test_m3u_probe.py passes against the fixed source.

### fix
src/SMS_ContainerM3U.c line 431, replace
    if (   !lpNode || SMS_ListFind (  lpNewList, _STR( lpNode )  )   ) continue;
with
    if ( !lpNode ) break;
The duplicate check is redundant: the node is removed from lpList right after being copied, so it cannot be picked twice. lpNode is never NULL here (lIdx < lSize == lpList->m_Size); `break` just makes that path terminate instead of spinning. Duplicate-titled entries keep their own m_Param (path), exactly as they already do with shuffle off.

### test
Add one case to tools/test_m3u_probe.py (validated in the private tree: times out on current source, passes with the fix). In the C `main`: replace the line `input->data=selecting?"track.mp3\nnext.mp3\n":"track.mp3\n";` with

The existing 10 s subprocess timeout turns the hang into a failure. On console: put song.mp3 and song.ogg in one folder, enable Randomize playlist, Play all -> Audio.

## #2 Shuffle seed is always a multiple of 8, biasing the first random draw (one track/order favoured up to 1.6x)
- issue: 25
- severity: low
- category: bug
- files: ['src/SMS_GUICmdProc.c', 'src/SMS_ContainerM3U.c']
- reproduced: True
- confidence: 0.9
- risk: Negligible: a 64-bit right shift on the seed only. Shuffle still differs per boot/per press (seed is the 125 Hz tick count at the moment of the action).

### evidence
All three shuffle sites seed with `g_RandSeed = ( int )g_Timer;` (SMS_GUICmdProc.c:151 continuous audio, :225 Play all -> Video; SMS_ContainerM3U.c:424). g_Timer only ever advances by 8 (src/SMS_Timer.s _timer_handler: `daddiu $v0, $v0, 8`; 125 Hz), so its low 3 bits are always 0. SMS_rand (include/SMS.h:174-176) is `( 161140751 * g_RandSeed + 13 ) % 219441163` in 32-bit int; I compiled it with the pinned ee-gcc 3.2.3 (-O2 -S) and it is `mult` (low 32 bits) / `addu 13` / signed `div` + `mfhi`, then `divu` by n. With the low seed bits fixed, the first output is visibly non-uniform modulo multiples of 4.

REPRODUCED on host by running the real _start_player and _start_playlist with that exact arithmetic and 8 ms timer ticks (.../i25-shuffle-playlist/cmdproc_real_rng.py):
  CURRENT: continuous audio, 9 tracks, 400000 picks: t06=15.38% ... t04=9.27% (max/min 1.66); 5 tracks: 22.6% vs 17.0% (1.33)
  CURRENT: Play all -> Video, 4 files: least/most likely order = 0.815 / 1.234 of expected (chi2=25836, df=23)
  seed = g_Timer >> 3: 9 tracks 11.05%-11.16% (max/min 1.01); 4 files 0.993 / 1.007 (chi2=17, df=23)
Standalone check (lcg2.c/lcg3.c): single pick with n=8 or 16 gives one slot 1.63x expected; n=4/12 1.23x; other n within noise. Continuous audio is hit hardest because it reseeds and takes exactly one draw per track.

### fix
Drop the three constant zero bits when seeding, at all three sites:
  src/SMS_GUICmdProc.c:151   g_RandSeed = ( int )g_Timer;  ->  g_RandSeed = ( int )( g_Timer >> 3 );
  src/SMS_GUICmdProc.c:225   same change
  src/SMS_ContainerM3U.c:424 same change
Nothing else. Do not change SMS_rand itself (also used by SMS_PlayerBallSim.c).

### test
No CI test recommended (the defect is statistical). Verification harness: wsl -d Debian -- bash -lc "cd (investigator scratch, not kept)/i25-shuffle-playlist && setarch -R python3 cmdproc_real_rng.py <path to SMS_GUICmdProc.c> 9 5 3" - max/min play share should be ~1.01 and the 4-file chi2 below ~45. tools/test_playlist_playback.py still passes with the change (its toy RNG yields a non-identity order for seed 123>>3). PS2 build with the change links cleanly.
