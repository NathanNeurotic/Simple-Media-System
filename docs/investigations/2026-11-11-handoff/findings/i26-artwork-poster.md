# i26-artwork-poster

Read-only review of the issue #26 artwork/poster code (PR #34 d7d51f9, PR #52 0e2c652, PR #53 1295be2/708fc17/70fe0f5/90ac063, plus the artwork ride-along edits in c275476) at branch fix/open-issues-2026-11 (HEAD c275476). Nothing in the repository was edited, committed or posted; all trial work was done in scratch copies. No PS2 console or emulator run was made, so nothing here is hardware-accepted.

RESULT: one real, host-reproduced defect (medium), one low-severity resource/latency issue found by code reading, one documentation gap. No memory-safety, VRAM or DMA defect could be substantiated.

1) REPRODUCED (medium): leaving the grid/poster view with R2 (and, less often, going back with Triangle to a level that was entered from grid/poster view) puts the ordinary list into a window state the legacy list navigation never produces (selection on the dimmed first row, m_pFirst == m_pCurrent with a previous entry, m_YOffset 0). The next UP drives m_YOffset negative: the highlight is drawn above the list panel (Y=28, -6, -40) and the really selected file is not among the rendered rows, so Cross would open a file the user cannot see. Present since PR #34. A 6-line inline fix was trialled in a private tree copy: repro shows the selection stays visible, the six artwork host tests still pass (PASS=6 FAIL=0) and the pinned ps2dev v1.0 Docker build links SMS.elf with no new warning.
2) NOT reproduced, code reading (low): Circle on a video in grid/poster view frees the artwork cache, then the subtitle picker repaints the browser, which re-reads and re-decodes the page's JPEGs right before playback and leaves the cache allocated during playback - the opposite of what line 1045 intends.
3) Docs (low): wiki/Video.md still describes R2 as a two-state list/grid toggle and never mentions the selected-poster view (PR #53) or that matching Movie.jpg/.jpeg sidecars are now hidden from the browser in every view (PR #52), including sidecars that are too large/progressive to be used as artwork and therefore can no longer be opened in the picture viewer.

RULED OUT (code reading unless stated):
- src/SMS_Artwork.c helpers (JPEG preflight, thumbnail/poster samplers, name builder, move clamp): host ASan/UBSan fuzz clean ("preflight: 1200463/3000000 accepted, no ASan fault", "samplers: 441 dimension pairs (41 rejected >512), no ASan fault", "name: bounds ok", "move: clamped").
- GS texture budget: the transient scratch texture at TBP 0x3FC0..0x4000 (already used by GUI_DrawIcon for 48x48 icons) is above the largest GUI framebuffer + font in every video mode by arithmetic (1080i CT16 ends 0x3C00, 720p CT24 ends 0x3DC0); 64x64 PSMCT32 fits exactly. Arithmetic only, not hardware.
- DMA/cache coherency: _artwork_packet qword layout matches GUI_DrawIcon; 90ac063 (SMS_SyncMalloc before UNCACHED_SEG writes) is correct; every free of pixels/packets is preceded by _artwork_drain (DMA_Wait VIF1+GIF); cache is cleared on every mode switch so 16 KiB thumb and 96 KiB poster buffers never mix.
- VU state: JPEG decode clobbers VU0 vf31; _artwork_restore_gs reloads it from the 16-byte-aligned GS_Params()->m_AspectRatio; no other VU1 user in the GUI; MPEG4 reloads VU0 at codec init; GUI does not use the scratchpad the decoder uses.
- Clock suspend/resume is not nested on the artwork path; progress indicator is not active during decode.
- R2 binding: handler matches R2 exactly, so SELECT|R2 and the four-shoulder combo do not collide; menus consume pad events while open; R2 reaches the browser through the GUI_Run broadcast when the device menu has focus (intended).
- Empty folder / device removal in grid and poster view; reload and refill paths (covered by tools/test_browser_reload.py and tools/test_browser_artwork_lifecycle.py, both pass).
- Sidecar matching: case-insensitive, .jpg/.jpeg only, only against video entries with the same stem, name-length bounded (tools/test_artwork_sidecar_filter.py passes). Cost is O(pictures x entries), the same order as the legacy per-video subtitle lookup, so thousands of files do not introduce a new complexity class.
- Blocking decode on slow/disconnected storage: synchronous by design (up to six <=256 KiB reads per grid page, one per newly selected row in poster view), bounded and documented in wiki/Video.md; not a defect, but never measured on hardware.
- Observation only, no fix proposed: "Play all" from the folder context menu (SMS_GUICmdProc.c, direct SMS_OpenMediaFile calls) does not release the artwork cache (<=96 KiB in grid view, up to 6 x 96 KiB in poster view if every row of the page was visited); releasing it would need a new exported function, which is not worth it without a measured memory problem.

AWAITING REPORTER/HARDWARE TEST: issue #26 is a feature request with no comments at all, so no artwork code has ever been confirmed on a console. Everything is untested on hardware: PR #34 (d7d51f9 and its follow-ups 1d0855c, a65ee0a, 3b8233d), PR #52 (0e2c652 sidecar hiding), PR #53 (1295be2 selected-poster view, 708fc17 R2 three-state cycle, 70fe0f5 caption sizing, 90ac063 poster packet sync) and the c275476 ride-along changes (_poster_render full-page cache keys, _is_video_artwork prefilter). wiki/Video.md itself says console acceptance is pending. Specific things only a console can settle: scratch-texture placement in 720p/1080i, VIF1 upload chain timing, decode latency on USB/MX4SIO/SMB, returning from playback into grid/poster view.

Scratch artefacts (outside the repo): (investigator scratch, not kept)/i26-artwork-poster\repro_r2_list.py and (investigator scratch, not kept)/i26-artwork-poster\repro_back.py (host repros, argv[1] = repo WSL path, optional argv[2] = alternative SMS_GUIFileMenu.c); (investigator scratch, not kept)/i26-artwork-poster\fixed\SMS_GUIFileMenu.c (patched copy with the trialled fix for finding 1); (investigator scratch, not kept)/i26-artwork-poster\fuzz_art.c (helper fuzz).

## #1 R2 back to list view (and Triangle-back to a level entered from grid/poster view) leaves an invalid list window; UP then moves the selection off-screen
- issue: 26
- severity: medium
- category: bug
- files: ['src/SMS_GUIFileMenu.c', 'tools/test_browser_reload.py']
- reproduced: True
- confidence: 0.9
- risk: Low. Only the list-view window right after R2 or after a back navigation is affected; the selected file is unchanged, it is shown on the second row instead of the first when it has a predecessor (the same state ordinary UP scrolling produces). First entry of a folder (head, no predecessor) keeps first == current, offset 0. Grid and poster views are untouched. Declaration is at block start, so ee-gcc 3.2.3 accepts it (built with the pinned toolchain). Not verified on a console.

### evidence
Origin: PR #34 (d7d51f9), unchanged through PR #53 and c275476.

Decisive code, src/SMS_GUIFileMenu.c lines 1446-1454 (R2 handler):
  lpMenu -> m_ArtworkMode = ( lpMenu -> m_ArtworkMode + 1 ) % 3;
  if ( lpMenu -> m_ArtworkMode ) _artwork_position ( lpMenu );
  else { lpMenu -> m_pFirst = lpMenu -> m_pCurrent; lpMenu -> m_YOffset = 0; }

The legacy list code assumes the selection is never the first visible row when that row has a predecessor (that row is the dimmed 'more above' row, lines 645-658) and that m_YOffset is the row index of the selection. _step_up, lines 1379-1383:
  apMenu -> m_pCurrent = apMenu -> m_pCurrent -> m_pPrev;
  if ( apMenu -> m_pCurrent == apMenu -> m_pFirst && apMenu -> m_pCurrent -> m_pPrev ) apMenu -> m_pFirst = apMenu -> m_pFirst -> m_pPrev;
  else --apMenu -> m_YOffset;
With m_pFirst == m_pCurrent the new current is the node BEFORE m_pFirst, so the else branch runs and m_YOffset becomes -1; render uses lSelY = 62 + 34 * m_YOffset (line 635).

Second entry to the same state, Triangle/back, lines 1566-1568: m_pFirst = SMS_ListFind(filt, _STR(lpState)); m_pCurrent = SMS_ListFind(filt, lpInfo->m_pCurrent); m_YOffset = lpInfo->m_YOffset. _push_state (lines 836-843) saves whatever window the current view had; in grid/poster view _artwork_position (lines 117-118) makes m_pFirst the page start and m_YOffset = index % 6, so a folder entered from a selection at index 6, 12, 18... and left after switching to list view restores first == current with a predecessor and offset 0.

### fix
Two inline edits in GUIFileMenu_HandleEvent, src/SMS_GUIFileMenu.c (kept inline on purpose: a new helper function would have to be added to the extraction lists of tools/test_browser_reload.py and tools/test_browser_artwork_lifecycle.py, which was tried and fails to compile otherwise).

(1) R2 handler, line 1451. Before:
   else { lpMenu -> m_pFirst = lpMenu -> m_pCurrent; lpMenu -> m_YOffset = 0; }
After:
   else {
    /* List rows: the selection is never the dimmed "more above" first row. */
    SMS_ListNode* lpPrev = lpMenu -> m_pCurrent ? lpMenu -> m_pCurrent -> m_pPrev : NULL;
    lpMenu -> m_pFirst  = lpPrev ? lpPrev : lpMenu -> m_pCurrent;
    lpMenu -> m_YOffset = lpPrev != NULL;

(2) Triangle/back restore, directly after line 1568 ( lpMenu -> m_YOffset = lpInfo -> m_YOffset; ) inside the if ( lpNode ) block, add:
     /* A level saved in a grid/poster view can start its page on the selection. */
     if ( !lpMenu -> m_ArtworkMode && lpMenu -> m_pCurrent == lpNode && lpNode -> m_pPrev ) {
      lpMenu -> m_pFirst  = lpNode -> m_pPrev;
      lpMenu -> m_YOffset = 1;
     }
Nothing else changes; grid/poster views already renormalise through _artwork_position on every render. The exact patched file used for the trial is (investigator scratch, not kept)/i26-artwork-poster\fixed\SMS_GUIFileMenu.c.

## #2 Circle (choose subtitles) in grid/poster view re-decodes the artwork page just before playback and keeps the cache allocated while the video plays
- issue: 26
- severity: low
- category: perf
- files: ['src/SMS_GUIFileMenu.c', 'src/SMS_GUIMiniBrowser.c']
- reproduced: False
- confidence: 0.5
- risk: Low: one additional call to an existing cleanup that already runs on the same path a few lines earlier; packets freed are ones the next GUI_Initialize rebuilds after playback anyway. Not verified on hardware; the benefit is small, so this is safe to defer.

### evidence
Code reading only, not run. src/SMS_GUIFileMenu.c lines 1043-1048:
  if ( apMenu -> m_ArtworkMode ) GUIFileMenu_Cleanup ( ( GUIObject* )apMenu );
  if ( !SMS_OpenMediaFile ( _STR( apMenu -> m_pCurrent ), aFlags | SMS_FA_FLAGS_MSG ) && apMenu -> m_ArtworkMode ) _redraw ( apMenu, 0 );
The cleanup at 1045 is the documented release point (docs/investigations/2026-10-27-artwork-grid.md line 34-36: opening a file from the grid drains DMA and releases cached pixels). With SMS_FA_FLAGS_SUB (Circle / RC_SUBTITLE on a video, _action_avi line 1054) SMS_OpenMediaFile calls GUI_MiniBrowser (line 972) after that cleanup. When the folder has at least one subtitle-like file, src/SMS_GUIMiniBrowser.c line 181 ( lpMenu -> Redraw ( lpMenu ) -> GUIMenuSMS_Redraw -> GUI_Redraw ) and line 184 ( GUI_Redraw ( GUIRedrawMethod_Redraw ) ) run; GUI_Redraw (src/SMS_GUI.c lines 177-185) calls Render on every object, including the file menu, whose packets were just deleted, so _artwork_render/_poster_render call SMS_ArtworkPage + SMS_ArtworkGet -> _artwork_load again: up to six synchronous JPEG opens/reads (<=256 KiB each) and decodes in grid view, one in poster view, executed while the movie's file context is already open. Playback then starts with those pixels (up to 6 x 16 KiB, or 96 KiB for a poster) still allocated, because nothing clears the cache after the picker. No host test covers _perform_file_action (grep of tools/ finds none). Impact is small (extra delay before playback on slow storage, <=96 KiB held), hence low.

### fix
Smallest change that restores the intended release without altering the existing order, in _perform_file_action (lines 1043-1048). Before:
 if ( apMenu -> m_ArtworkMode ) GUIFileMenu_Cleanup ( ( GUIObject* )apMenu );
 if ( !SMS_OpenMediaFile ( _STR( apMenu -> m_pCurrent ), aFlags | SMS_FA_FLAGS_MSG ) && apMenu -> m_ArtworkMode ) _redraw ( apMenu, 0 );
After:
 void** lpParam;
 if ( apMenu -> m_ArtworkMode ) GUIFileMenu_Cleanup ( ( GUIObject* )apMenu );
 lpParam = SMS_OpenMediaFile ( _STR( apMenu -> m_pCurrent ), aFlags | SMS_FA_FLAGS_MSG );
 if ( !apMenu -> m_ArtworkMode ) return;
 /* The subtitle picker repaints the browser, which reloads the page. */
 if ( lpParam ) GUIFileMenu_Cleanup ( ( GUIObject* )apMenu );
 else _redraw ( apMenu, 0 );
