# hunt-player-sync

Read-only hunt of the playback core (SMS_Player.c, SMS_PlayerControl.c, SMS_SPU.c, SMS_IPU.c, SMS_RingBuffer.c, SMS_VideoBuffer.c, SMS_PCM.c, SMS_Timer.s; SMS_PlayerMenu.c, SMS_SubtitleContext.c and SMS_IPU_1.c were only diff-reviewed against 2.9rev4, where the fork changes are type/buffer-size edits). No repository file was touched. Nothing was run on a PS2 or emulator; no finding below has hardware acceptance.

Main result: one substantiated fork regression in the audio RPC layer. SPU_RPC_TIMEOUT in src/SMS_SPU.c is 180 g_Timer units, which the comment and commit c76cf00 call "~3 s" but which is 180 ms (g_Timer counts milliseconds). The embedded AUDSRV makes a second UI-sound RPC wait until the previous sound has finished (0.8-0.9 s for Error/Mount/UMount), so overlapping UI sounds trip the timeout and permanently retire the audio server for the session: no UI sounds, and movies play silent with no audio clock. UI sounds default ON. One-line fix. Second: the two warnings at SMS_SPU.c:177-178 have a one-line, semantics-identical fix.

Issue #10 (audio loops, video frozen): the loop itself is explained and is inherited. The AUDSRV blob is byte-identical to 2.9rev4 and its play thread has no underrun detection, so when the EE stops feeding PCM it replays its ~18 KB ring forever. That is a downstream symptom of an EE stall (crash, or a same-priority thread spinning without yielding); the actual stall in the reporter's Handbrake MP4 could not be identified without the file. I found no small, reliable EE-side stall detector and recommend none.

Ruled out / inherited and not reported: _terminate_threads ordering (equivalent to upstream under cooperative same-priority scheduling); the fork's rewritten video-output drain loop (covered by tools/test_player_video_drain.py); pause handshake races (upstream); A/V sync in IPU_VBlankStartHandler (unchanged apart from s64/u64 types); 32-bit timeline overflow (the clocks are int64 ms; MPEG-PS _Seek takes a uint32 ms position, fine up to 49 days); A/V packet-queue deadlock (broken by StopSync when the audio queue empties); SMS_PCM.c (identical to upstream); SMS_Timer.s (register renames only); IPU_StopSync asm reorder (harmless); MOV _ReadPacket returning 0 (it returns -1, so the main loop does not spin there); ScrollBar float divide by zero (no FPU trap on R5900, only for durations under ~130 ms).

Observed but NOT substantiated enough to report: (a) the "slight slowdown" at seconds 10-16 on USB in #24 - no pacing defect found in the player core; worth asking the reporter whether that run had sound, since finding 1 would give silent, unpaced playback if two mass devices were attached at boot; (b) SMS_Player.c:785 adds m_AVDelta on every audio packet including NOPTS ones, so a non-zero user A/V offset may accumulate on containers that deliver NOPTS audio packets (inherited; default offset 0; I did not establish which containers do this); (c) MPEG-PS probe start-PTS min loop could pick SMS_NOPTS_VALUE if a stream lacks a head PTS (container scope, untested).

The only later change to the playback core is c275476 "fix: stop playback workers before scrollbar seek reset (#51)" (2026-11-06), which targets exactly the reported "seek backward after pausing, then resume freezes" case; it is covered by tools/test_player_scrollbar_seek.py on host but unverified on hardware. ## #1 SPU_RPC_TIMEOUT is 180 ms, not ~3 s: overlapping UI sounds permanently retire the audio server (silent, unpaced playback)
- issue: 0
- severity: high
- category: bug
- files: ['src/SMS_SPU.c', 'src/SMS_Timer.s', 'src/SMS_Sounds.c', 'src/SMS_GUIDevMenu.c', 'src/SMS_GUIDesktop.c', 'src/SMS_GUIFileMenu.c']
- reproduced: False
- confidence: 0.8
- risk: Very low. On a healthy console the wait returns as soon as the RPC completes, exactly as before; the only change is that a queued UI sound waits (as upstream did) instead of killing audio. On the PSX freesd lost-interrupt case the one-off UI freeze before going silent grows from 0.18 s to 3 s, which is what the original commit intended.

### evidence
Fork regression from c76cf00 (2026-07-28; upstream 2.9rev4 used unbounded WaitSema). src/SMS_SPU.c:96 `#define SPU_RPC_TIMEOUT 180   /* vblank ticks, ~3 s NTSC ... */`, used at :100-105 `u64 lEnd = g_Timer + SPU_RPC_TIMEOUT; while ( PollSema ( aSema ) < 0 ) if ( g_Timer > lEnd ) { apClient -> server = NULL; return 0; }`. g_Timer is not vblank ticks: src/SMS_Timer.s:49-50 programs Timer0 mode 0x01C2 (BUSCLK/256) with compare 0x1200 and :184 does `daddiu $v0, $v0, 8` per tick, i.e. 125 Hz x 8 = milliseconds (the rest of the code agrees, e.g. `g_Timer - lTimer > 2000` in SMS_GUI.c). The commit message states the intent as '~3s'. Why 180 ms is too short: disassembly of the embedded AUDSRV (byte-identical to the 2.9rev4 blob) shows RPC func 4 (UI sound, 0x824) does WaitSema on the bss+0x3634 token at 0x844-0x854 and never signals it; only the SPU2 IRQ handler (0x7dc) returns the token when the voice reaches its end address. So a second UI-sound RPC blocks in the IOP until the first sound has finished. Ran scratch script spu_timeout_check.py against the tree; it printed: 'timer0 mode=0x1c2 compare=4608 -> 125.0 Hz, g_Timer += 8 per tick -> 1.000 units per ms', 'SPU_RPC_TIMEOUT = 180 g_Timer units = 180 ms', sounds 903 ms (Error), 44 ms (PAD), 817 ms (Mount), 815 ms (UMount), 'RESULT: FAIL (timeout shorter than longest UI sound)'. Triggers in the default config (SMS_Config.c:532 sets SMS_BF_SDFX on): two mount events drained back to back (SMS_GUIDevMenu.c:366 plays Mount for dev 0/4/6; SMS_IOP.c:655-658 flags every connected mass unit at boot, and SMS_GUI.c:874-882 posts them one after another); X/O/triangle in the browser (SMS_GUIFileMenu.c:1504/1513/1546) within ~0.6 s of a mount/unmount sound; a file press within ~0.7 s of an error dialog (SMS_GUIDesktop.c:869, dismissable after 200 ms). Consequence: s_ClientDataA.server = NULL, and SPU_Initialize is only called once from SMS_IOP.c:1665, so audio stays dead until reboot; SPU_PlayPCM then returns immediately (SMS_SPU.c:190), so movies are silent and lose the audio clock that paces video (the fork's own comment at :185-189 describes this). The same 180 ms bound also guards SPU_SetVolume/Silence/Shutdown/Destroy/LoadData against a merely busy IOP. Not reproduced on hardware; the two-device boot case additionally depends on the first device's directory listing finishing in under ~0.6 s.

### fix
src/SMS_SPU.c:96: `#define SPU_RPC_TIMEOUT 3000   /* ms ( g_Timer counts milliseconds ) -- far beyond any healthy reply, and beyond the longest UI sound a queued one must wait for */`. One line plus the comment; matches the intent stated in c76cf00. No other change needed.

### test
Add a host test (e.g. tools/test_spu_rpc_timeout.py, modelled on the scratch spu_timeout_check.py) that derives ms-per-g_Timer-unit from SMS_Timer.s, computes each g_SMSound duration as size/16*28/48000 s from SMS_Sounds.c, and asserts SPU_RPC_TIMEOUT in ms is at least 1000 and greater than the longest sound. It fails today (180 < 903) and passes with 3000. On hardware: boot with two mass devices attached or press X right after a mount/error sound, then play a file and confirm sound is present.

## #2 SMS_SPU.c:177-178 'assignment makes pointer from integer without a cast' warnings
- issue: 0
- severity: low
- category: cleanup
- files: ['src/SMS_SPU.c']
- reproduced: True
- confidence: 0.95
- risk: Negligible: (x << 4) >> 4 on a 32-bit unsigned equals x & 0x0FFFFFFF, so generated behaviour is unchanged.

### evidence
src/SMS_SPU.c:177-178: `apData = ( unsigned int )apData << 4;` / `apData = ( unsigned int )apData >> 4;` assign an unsigned int to `void* apData`. Both warnings appear in the ps2dev docker build log (scratchpad/build/base.log lines 2-3). Upstream 2.9rev4 wrote the same operation as a cast-as-lvalue (`( unsigned int )apData <<= 4; ... >>= 4;`); the fork's rewrite kept the behaviour (clear the top 4 address bits, i.e. strip the KSEG/uncached prefix before handing the buffer to SIF2 DMA) but lost the cast back to a pointer. Behaviour is correct; only the diagnostics are wrong.

### fix
Replace both lines with one: `apData = ( void* )(  ( unsigned int )apData & 0x0FFFFFFF  );` - identical result on the 32-bit EE, no warning.

### test
Rebuild with scratchpad/ps2make.sh and confirm the two SMS_SPU.c warnings are gone and no new ones appear; existing host tests unaffected (the function is PS2-only).

### VERDICT

Not independently checked (below the verification cut-off, or its checker did not finish).

## #3 Issue #10 audio loop is AUDSRV replaying its ring after the EE stops feeding it (inherited); the EE stall itself is not identified
- issue: 10
- severity: medium
- category: bug
- files: ['src/SMS_Data.c', 'src/SMS_SPU.c', 'src/SMS_Player.c']
- reproduced: False
- confidence: 0.7
- risk: None (no change proposed).

### evidence
Extracted the embedded AUDSRV IRX from src/SMS_Data.c (offset 221232, 8989 bytes) and disassembled it with iop-objdump; the blob is byte-identical to the one in upstream 2.9rev4, so this behaviour is inherited. The block-transfer play thread (0x200) converts ring data at the read position into the idle half of its 4096-byte buffer on every SPU2 transfer interrupt and advances/wraps the read position without ever comparing it with the write position: there is no underrun detection or silence fill. When the EE stops calling SPU_PlayPCM (the writer at 0x5a4/0x1b4 is the only thing that advances the write position), the last ~18 KB of PCM repeats forever, which is the reported 'audio started looping strangely, as if the console had crashed' with frozen video. The loop is therefore a symptom of an EE-side stall: an EE exception, or one of the same-priority cooperative threads (main/VD/AD/AR at SMS_THREAD_PRIORITY 64, no time slicing) spinning without yielding. One inherited spin exists in the main loop, src/SMS_Player.c:1401-1403 (`lSize = ReadPacket (...); if ( lSize <= 0 ) continue;`), which never yields while a demuxer keeps returning 0, but src/SMS_ContainerMOV.c _ReadPacket returns -1 rather than 0, so that is not shown to be the #10 path. Without the reporter's file I could not determine what stalls at 0:35; nothing was reproduced.

### fix
No code change recommended from this analysis. A reliable in-player stall detector is not available cheaply: thread-level watchdogs do not run when the EE threads are starved, issuing an RPC from interrupt context is unsafe, and the proper fix (silence on underrun) lives in the source-less AUDSRV binary. Next step is evidence: ask the reporter to retest current master and, if it still freezes, say whether triangle/stop still responds (distinguishes a spinning thread from an EE crash) and share the file or the exact Handbrake settings so the MOV demux/decoder path can be run on host.

### test
None applicable until the stall is reproduced; if a sample file is obtained, run it through the host MPEG-4/MOV harnesses to the 0:35 position.
