# i20-23-mpeg-colour

Read-only conformance audit of the software MPEG-1/2 path for #20/#23. Repo untouched (git status shows only the two pre-existing untracked items). No remaining host-reproducible colour-corrupting decoder defect was found at HEAD (c275476). The three PR #35 defects were real, are inherited from upstream SMS 2.9rev4 (not fork regressions), and the fix is bit-exact against FFmpeg on real converter-style streams. Nothing here is hardware acceptance.

WHAT WAS DONE
1) Binary diff with the pinned toolchain (ee-gcc 3.2.3, ps2dev/ps2dev:v1.0): at the reporter's last tested commit c942e1c the fork's libmpeg_core object code was identical to upstream 2.9rev4 (tag commit e8148e4e); today it differs only in the four PR #35 routines. libmpeg.c differs only by null checks plus the chroma-vector change; SMS_IPU.c/SMS_MPEG.c differ only in scratch-register spelling ($at/$t0 -> ASM_REG_T0 macros; SMS_MPEG.c is the MPEG-4 dequantiser, not on the MPEG-1/2 path); SMS_MPEG12.c/SMS_VideoBuffer.c differ by the frame-ownership wait, allocation-failure handling and s64/u64 types.
2) Host oracle that executes the REAL assembled EE object code of libmpeg_core.S (_MPEG_do_mc, all put/avg luma/chroma routines, put_block_fr/fl, add_block_frfr/frfl) in a small R5900 interpreter, driven by the REAL _mpeg12_get_ref C from src/libmpeg.c, compared with (a) an independent scalar H.262 7.6 predictor and (b) FFmpeg's own decoded output. Interpreter decode was self-checked against the source mnemonic sequence (0 diff lines). Only _MPEG_dma_ref_image (toSPR DMA of 2x2 reference macroblocks) is modelled as memcpy.
   - T1, 20,000 random cases (10,000 frame MC + 10,000 field-in-frame MC, half bidirectional, vectors +-70 half-pel): fork HEAD 0 mismatches (prediction luma/chroma, put_block_fr, add_block_frfr, put_block_fl, add_block_frfl). Upstream 2.9rev4: luma 0, chroma prediction wrong in 15,607 cases (13,353 with a negative odd vector component, 2,254 chroma-XY-half-pel only), put_block_fl chroma wrong in 1,303 cases.
   - T2, four mpeg2video streams made and decoded by FFmpeg 7.1.4 with the converter profile (640x480, 30 fps, 2500k, -bf 0, yuv420p; GOP 50/15/50/50; slow zoom and +-half-pel diagonal drift), 119 predicted frames each. For every textured macroblock whose luma equals exactly one motion-compensated candidate (+-6 px search) and whose Y+Cb+Cr equal the truncating H.262 prediction, production output must equal FFmpeg's. 57,269 such macroblocks: fork HEAD 0 luma / 0 chroma mismatches; upstream 2.9rev4 0 luma / 16,813 chroma mismatches (29.4%; max single-step chroma error 72/255; every one is either negative-odd vector or chroma-XY). FFmpeg matched floor-rounded chroma in 0 macroblocks, i.e. truncation is the correct convention.
3) Existing host tests run in WSL: tools/test_mpeg_motion_vectors.py, test_mpeg_skipped_motion.py, test_mpeg_color_feed.py, test_mpeg12_frame_lifetime.py -> PASS=4 FAIL=0.
4) Reporter recordings: YouTube auto-stills of the reporter's own 2.9rev4 recording for #23 (CKCdjMpOUzI, still 3) show the same chroma smear as the fork recording (d94FdsJjCPE, still 3) while still 2 of both is clean; the clip is a slow zoom (sub-pel vectors around -1), exactly the case the upstream chroma bugs hit on every P-frame and accumulate until the next I-frame. The reporter never states in text that 2.9rev4 is correct. #20 stills were inconclusive at thumbnail resolution.

RULED OUT (reading plus the tests above unless noted)
- Motion-vector decode/predictor resets, skipped-MB handling (P and B), no-MC P macroblock motion_type derivation, DC predictor reset (m_fDCRst), BDEC command word (MBI/DCR/DT/QSC), intra_dc_precision (IDP), q_scale_type/intra_vlc_format/alternate_scan (QST/IVF/AS), picture type (PCT), MPEG-1 flag, quant-matrix load/default tables (SETIQ) - all identical to upstream and consistent with H.262 by reading.
- Chroma vector derivation and chroma source addressing after PR #35: algebraically equal to the spec; ChromaX reaches 8 only when the chroma half-pel bit is 0, so the 2x2 transferred macroblock window is never exceeded (also exercised by T1).
- CSC DMA continuation for >1023 macroblocks (batches of min(1023, remaining), 384 bytes in / 1024 or 512 out per MB): correct by reading; prior PCSX2 run at 1,200 MBs passed. Not re-run here.
- $at -> $8 inline-asm changes and .set at: disassembly shows register renames only.
- Frame-buffer ownership: fixed by a433154; covered by test_mpeg12_frame_lifetime.py (host model only).
NOT VERIFIABLE ON HOST: IPU hardware IDCT/BDEC output and CSC arithmetic, GS presentation, real-console timing. Coded-macroblock reconstruction is covered only for the add/store routines with synthetic residuals. No reporter file was available, so no claim is made that #20's green is the same mechanism.
Unreported upstream-identical oddities (no evidence they affect converter output, not findings): field-PICTURE dual-prime calls _mpeg12_get_ref with aH=16 (non-interleaved addressing, aFDst=1) which looks wrong by reading but cannot be produced by FFmpeg; _MPEG_Set16 patches four immediates through one shared %hi (fine in the current link layout); _MPEG_SetPCT uses bltzl rather than a linking branch to _ipu_sync.
