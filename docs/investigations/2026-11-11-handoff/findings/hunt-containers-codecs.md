# hunt-containers-codecs

Read-only hunt; repo untouched (HEAD c275476, git status unchanged). No PS2/emulator run: everything below is HOST evidence only, never hardware acceptance.

METHOD. Built a 64-bit Linux (WSL gcc 14) ASan + UBSan(bounds, null, integer-divide-by-zero) harness that compiles the REAL production sources (SMS_Container.c, all SMS_Container*.c incl. MPEG_PS/MOV, SMS_Codec.c, SMS_WMA/AAC/FLAC/OGG/AC3/DTS/MP123.c, verbatim STIO_Read/File_Skip/File_GetString/SMS_ContID/SMS_Realloc) from a private tree copy; only MIPS inline asm was replaced. Memory-backed FileContext models the fork's STIO_Seek (dev 0 = FAT clamp/fail, dev 1 = permissive), with SIGALRM watchdog and I/O budget. Corpus: 49 ffmpeg-made files (AVI x6, ASF/WMV/WMA x4, MP3/MP2 x5, OGG x4, FLAC x3, AAC x2, M4A/MP4 x4, AC3 x2, DTS, MPEG-PS x5, m2v, ts, mkv, flv, jpg, png, wav, m3u, txt, zeros, random). Mutations: truncations, header byte flips, 32-bit field stomps, body bit flips, tail stomps, both seek models. Everything is under (investigator scratch, not kept)/hunt-containers-codecs/ (fixes.py holds every trialled before/after string; crafted/ holds single-field repro files; fuzz.py, matrix.py, build.sh, h/main.c are the harness).

RESULT. Baseline (repo code): 39,060 mutated runs gave 6 distinct memory-safety/hang defects plus more found by targeted crafting. With all 12 one-to-five-line fixes applied in a private tree (tree_g): 74,954 mutated runs with LeakSanitizer and codec Open+Init enabled, plus 110,846 runs on the previous tree, produced 0 crashes, 0 hangs, 0 leaks; the detection matrix for all 49 valid files under 13 extension hints x 2 seek models is byte-for-byte identical to baseline (same container, same bytes read). Nearly all defects are upstream-latent (ps2homebrew 2.9rev4 has the same code), not fork regressions.

RULED OUT / NOT FINDINGS.
- Extension-hint reordering: no misdetection of any valid file under any of 13 hints (bin/avi/mpg/mp3/ogg/wma/m4a/mp4/aac/ac3/m3u/jpg/flac) in either seek model.
- Valid corpus: every supported type detected correctly; no leaks on accept or reject paths (LSan), natural name and .bin.
- Fork STIO_Seek failure semantics on truncated AVI: realistic truncations (mid-movi, mid-idx) stay bounded (16 seeks); only tiny files cut inside the header JUNK padding read up to ~1 MB on the FAT model. Not reported.
- AVI failed-header stale streams: no leak/crash seen under LSan across mutations.
- FLAC sample-rate-0 division, SMS_Rescale(INT64_MIN) recursion: never reached in ~7k FLAC / all mutations.
- OGG, FLAC, AC3, JPG, M3U containers: no crash/hang/leak (M3U accept path under mutation was not exercised because sibling files are absent in the fuzz layout; valid playlists parse fine).
- Decoder Open+Init for AAC, FLAC, Vorbis, WMA, AC3: no memory errors under header mutations. LIMITS: Decode() was not exercised (PS2 asm kernels and VLC are stubbed); MP3/MP2 Open uses fixed PS2 addresses and cannot run on host; DTS had no reachable corpus file.
- SMS_Container.c:239 division by m_BitRate==0 fires on an ordinary ffmpeg AVI with two MP3 tracks, and SMS_ContainerASF.c:368 '% packet_size' fires on corrupt ASF; both are non-trapping on EE (-mno-check-zero-division, Makefile:15) and the first only feeds packet m_Duration. Benign, not reported as findings.
- Observed but not root-caused (MPEG-PS owner's file): the PS probe reads the ENTIRE file before rejecting unhinted non-PS files that contain 00 00 01 start codes (elementary.m2v 864,287 bytes read of 864,287; mkv 255,452; flv 267,163; ts 426,381) versus ~100 KB for files without start codes. Same structure exists upstream.

## #1 ASF header: Stream Bitrate Properties uses 'flags * 0x7F' as array index (heap out-of-bounds write on ordinary multi-stream WMV)
- issue: 0
- severity: high
- category: bug
- files: ['src/SMS_ContainerASF.c']
- reproduced: True
- confidence: 0.9
- risk: Very low: valid indices become 0..127 as in ffmpeg. What exactly the stray write corrupts on a real PS2 depends on heap layout and was not observed; removing it can only remove corruption.

### evidence
src/SMS_ContainerASF.c:325-328:
    int lFlags   = File_GetUShort ( lpFileCtx );
    int lBitRate = File_GetUInt   ( lpFileCtx );
    int lStmID   = lFlags * 0x7F;
    lpASF -> stream_bitrates[ lStmID ] = lBitRate;
stream_bitrates is 'uint32_t stream_bitrates[ 128 ]' inside the calloc'd ASFContext (line 90). ffmpeg's original is 'flags & 0x7f'. Stream number 1 -> index 127 (last valid slot), stream number 2 -> index 254, i.e. roughly 290 bytes past the end of the ~984-byte context block; stream 3 -> index 381. The Stream Bitrate Properties object (GUID s_GUID[10], CE 75 F8 7B ...) is written by Microsoft encoders into normal WMV/WMA files; ffmpeg's muxer does not write it, so I inserted a standard one (2 records, stream numbers 1 and 2) into the ffmpeg-made wmv2_wmav2.wmv (craft_asf.py -> crafted/wmv_bitrate_1_2.wmv). Running the real probe printed: 'SMS_ContainerASF.c:328:29: runtime error: index 254 out of bounds for type uint32_t [128]' in asf_read_header <- SMS_GetContainerASF <- SMS_GetContainer. The same file with only stream 1 (crafted/wma_bitrate_1.wma) parses cleanly. Identical line exists in upstream 2.9rev4 (line 325), so this is upstream-latent. The inner 'int lBitRate' also shadows the outer 'uint32_t lBitRate[128]', which therefore stays all-zero.

### fix
One character. Before: 'int lStmID   = lFlags * 0x7F;'  After: 'int lStmID   = lFlags & 0x7F;'. Trialled in private tree: crafted/wmv_bitrate_1_2.wmv then reports 'RESULT ASF nstm=2 ...' and reads 50 packets with no sanitizer report; all 4 valid ASF corpus files unchanged. (The shadowed, never-filled outer lBitRate[] fallback is a separate dead-code matter; leave it.)

### test
Host test in the style of tools/test_mpeg_ps_probe.py: compile real SMS_ContainerASF.c with a memory FileContext under -fsanitize=address,bounds, feed a minimal ASF header containing a Stream Bitrate Properties object listing stream numbers 1 and 2, expect clean parse. Scratch repro: craft_asf.py + runf.sh.

## #2 AVI _ReadPacket: stream number and chunk size are never both validated (lCond uses '+' and the wrong digits) -> m_pStm[] out-of-bounds and unbounded read into the packet buffer
- issue: 0
- severity: high
- category: bug
- files: ['src/SMS_ContainerAVI.c']
- reproduced: True
- confidence: 0.9
- risk: Low. For well-formed files both sub-conditions were already true, so behaviour is identical (verified: same packet count/bytes on 6 AVIs). Chunks naming a non-existent stream or a negative size are now skipped byte-wise instead of dereferenced.

### evidence
src/SMS_ContainerAVI.c:796-797:

  lCond  = (  lCount < ( int32_t )apCont -> m_nStm  ) + (  i + lSize <= ( uint32_t )lpAVICont -> m_MoviEnd  );
lCond is computed from the 'ix##' digits (lData[2..3]) and with '+' (logical OR), then reused at line 815 for the '##dc/##wb/..' branch after lCount has been recomputed from lData[0..1]. For a normal chunk '00dc', lData[2..3]='dc' gives lCount=571, so the stream test is always false and lCond is just the size test; the real stream number is never checked before line 818 'SMS_Stream* lpStm = apCont -> m_pStm[ lCount ];' (lCount 0..99, array of 8). lSize is int32_t straight from the file and 'i + lSize' wraps, so a negative size passes and reaches line 824 'lpBuf -> Read ( lpBuf, lpPkt -> m_pData, lSize )' with a ~4 GB unsigned count, i.e. the rest of the file is copied over the packet ring buffer. ffmpeg's original has 'n < s->nb_streams && i + size <= avi->movi_end'. Reproduced with single-field edits of the valid xvid_mp3.avi (craft2.py): chunk id '21dc' -> 'runtime error: index 21 out of bounds for type SMS_Stream *[8]' at the m_pStm[lCount] line; '05dc' -> 'member access within null pointer of type struct SMS_Stream'; chunk size 0xFFFFFFF0 -> 'AddressSanitizer: heap-buffer-overflow ... memcpy <- STIO_Read <- _ReadPacket'. The fuzzer hit the same two UBSan sites from random body bit flips (dx50_ac3.avi bflip17/bflip108). Same code upstream.

### fix
Three lines, restoring ffmpeg's semantics.
Line 797 before: 'lCond  = (  lCount < ( int32_t )apCont -> m_nStm  ) + (  i + lSize <= ( uint32_t )lpAVICont -> m_MoviEnd  );'
after: 'lCond  = lSize >= 0 && i + lSize <= ( uint32_t )lpAVICont -> m_MoviEnd;'
Line 802 (ix branch) before: '       lCond' after: '       lCond && lCount < ( int32_t )apCont -> m_nStm'
Line 815 before: '       ) && lCond' after: '       ) && lCond && lCount < ( int32_t )apCont -> m_nStm'
Trialled: all three crafted files then play to EOF ('PACKETS n=255 total=376868', identical to the unmodified file); all 6 valid AVIs unchanged.
