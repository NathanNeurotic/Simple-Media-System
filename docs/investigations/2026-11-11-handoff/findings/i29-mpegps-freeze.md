# i29-mpegps-freeze

Issue #29 (.mpg MPEG-2 + AC3 from USB freezes at E70 "getcontainer", plays in SMS 2.9rev4) - read-only investigation; repository untouched (git status unchanged at c275476). No PS2 hardware or emulator was used: everything below is host-reproduced with the REAL STIO + SMS_ContainerMPEG_PS.c code under ASan/UBSan plus static disassembly of the shipped IRX binaries. Nothing here is hardware-accepted.

ROOT CAUSE FOUND (mechanism reproduced on host; driver behaviour proven from the shipped binaries): on the fork's BDM storage path, fileXioLseek() is a signed 32-bit API. irx/bdmfs_fatfs.irx's 32-bit lseek sign-extends the offset (`sra a3,a1,0x1f`) into its lseek64, and FatFs f_lseek clamps a read-only seek beyond the file size to end-of-file. So any SEEK_SET at or above 0x80000000 lands on EOF. The MPEG-PS probe always seeks to m_Size-0x1FFFF to scan tail PTS. For a file of 2 GiB+128 KiB up to 4 GiB, at the reporter's commit 7b172d0 that seek hits EOF, every later read returns 0 bytes with no device I/O, and the (unchanged-from-upstream) `while(!FILE_EOF)` tail loop never terminates: spinner alive, USB activity light off, last crumb E70 - exactly the reported symptoms. SMS 2.9rev4 used its own USB FAT driver whose seek takes an unsigned position, so the same file plays there. Harness at 7b172d0 with a 2147614720- or 3221225472-byte virtual file: "HANG SPIN-ON-ZERO-BYTE-READS(no device I/O) ... zero_reads=2000001 clamped_seeks=1 dev_pos=<size> ctx.m_CurPos=<size-0x1FFFF>"; with an unsigned-seek device model the same code probes fine.

HONESTY LIMITS: the reporter never stated the file size (the VLC screenshot shows only 720x576 25 fps MPEG-2 + AC3 3F2M/LFE 48 kHz, E:\video.mpg). A 5.1 PAL MPEG-2 rip is plausibly 2-4 GiB but this is unconfirmed - ask the reporter for the exact byte size. Confidence that the mechanism and fix are correct: high. Confidence that it is this reporter's file: moderate. Every synthesized file under 2 GiB (ffmpeg vob/dvd/mpeg/svcd muxes, 5.1 and 2.0 AC3, MP2, two audio tracks, 473 KB to 98 MB, truncated, zero/junk tails) probes and demuxes to EOF without a hang at both 7b172d0 and HEAD.

BISECT (real code per commit): e71fc13 (PR #30, announced on the issue as the fix: "dangling m_pCtx") still hangs, in the tail scan (E51). 258a556 bounds the loop, so from there to HEAD the probe returns - but with duration=-1813430636 ms (no tail PTS) and any seek/resume past 2 GiB still fails (STIO_Seek returns -1 with the device descriptor left at EOF). So HEAD no longer freezes on such a file but is still broken for it; the reporter has not retested.

SECOND DEFECT FOUND WHILE TESTING (regression, same symptom class): commit 39d762f ("retry codec probes", 2026-10-26, after the reporter's build) made the PS probe drop and re-probe a video stream on every later packet when no sequence header is found; each retry repeats a ~1024-header forward walk. Rejected or mid-stream-cut program streams now read 1.8-7.35 GB before the probe returns (was 4-10 MB at 7b172d0 and 3db9048/b7fe5d0). Measured on real ffmpeg-made files: H.264+AC3 in PS 9 MB file -> 7,350,436,758 bytes read, 931 seeks; MPEG-4+MP2 -> 2.0 GB; 11 MB MPEG-2 stream cut after 5 packs -> 5.57 GB. At PS2 USB 1.1 speed (about 1 MB/s; estimate, not measured) that is an hour or more of spinner at E70. This is not the reporter's file (it post-dates their build and the drive light would keep blinking) but it is a new freeze for .mpg/.vob files.

RULED OUT: PS parser divergence from 2.9rev4 (7b172d0's SMS_ContainerMPEG_PS.c is functionally identical to upstream); probe ordering (.mpg hint puts the PS probe first, so no other probe runs before it); the "dangling m_pCtx double-free" as the cause of this hang; the USB read-ahead thread from PR #49 (only starts from Stream(), not during probing, and post-dates the report); any hang for sub-2 GiB well-formed files. The lseek64 path the fix relies on exists end to end in the shipped binaries: libfileXio RPC 28 -> filexio.irx -> iomanX export 30 -> bdmfs_fatfs lseek64 (device type 0x10000010); smbman and udpfs also declare FSEXT/lseek64.

CHANGES ON MASTER AFTER THE REPORTER'S LAST TEST (7b172d0, Oct 18) touching this path, all still awaiting reporter retest: e71fc13 (10-25), 234c787, fc2a02d, 3c2fcba, 258a556, c942e1c, 3db9048, b7fe5d0, 39d762f, 0033b80 (10-26), 93f8c5e, c1cb8d4, 59d0ed1, 1422165 (10-27), 8a25e22 PR #49 (11-01), c275476 PR #51.
