# i24-storage-throughput

Issue #24 storage-path investigation (read-only; repository untouched, `git status` shows only the two pre-existing untracked tool files; no GitHub posts). No console or emulator run was available: every timing statement below is from code reading, a host test harness or a toy model, NOT from hardware. Nothing here is hardware-accepted.

WHAT THE CODE DOES TODAY (current master c275476, storage path identical to the reporter's 8a25e22 build)
- USB (BDM driver-name ioctl == "usb"): 64 KiB fileXioRead per slot, 3 slots in the 192 KiB stream buffer, filled by a priority-62 helper thread (PR #49). Reader (main thread, prio 64) only memcpy-consumes.
- MX4SIO and every other non-USB `mass:` driver: `STIO_Fill` — the priority-64 main thread issues a synchronous chain of 4 KiB fileXioRead RPCs, 8 per 32 KiB refill. The video decoder, audio decoder and audio renderer are also priority 64 (SMS_Player.c:1832-1856); the MPEG-2 decoder busy-waits on the IPU and yields roughly once per frame. On the EE kernel equal-priority threads are not preempted, so when an RPC completes, the next request is not issued until the decoder yields. The SIO2/SD device therefore sits idle between 4 KiB requests. SMS 2.9rev4 needed the main thread once per 192 KiB (async fio, two buffers) — the fork's MX4SIO path needs it 48 times for the same bytes.
- RPC arithmetic (exact, from constants): 6 Mbps = 750,000 B/s -> MX4SIO 183 RPC/s in 22.9 refills/s; USB 11.4 RPC/s; 2.9rev4 3.8 async reads/s. 8 Mbps = 1,000,000 B/s -> MX4SIO 244 RPC/s in 30.5 refills/s; USB 15.3 RPC/s; rev4 5.1/s.
- Indirect hardware evidence for the mechanism: the only change between the reporter's c942e1c test ("USB still stutters") and 8a25e22 test ("USB now a slight slowdown") on USB was moving the reads to the prio-62 helper. MX4SIO was excluded from that change and "still stutters".

PROPOSAL (finding 1): let the existing helper serve every `mass:` file, with slot size = the file's own `m_FillLimit` (64 KiB USB, 32 KiB others). The helper loop already clamps each fileXioRead to `m_RdChunk`, so MX4SIO still only ever sees 4 KiB requests. ~20 changed source lines, no new thread, no new buffer, no new state. Validated only on host + PS2 link in a private scratch copy: full CI host list PASS=44 FAIL=0, new MX4SIO case fails on unpatched source and fails if the 4 KiB bound is removed, PS2 ELF links with baseline-identical warnings (18) and identical size. Scratch tree: (investigator scratch, not kept)/i24-storage-throughput/tree (patch scripts patch1.py and patch_tests.py beside it).

Toy scheduler model ((investigator scratch, not kept)/i24-storage-throughput/sched_model.py; assumed inputs T = ms per 4 KiB RPC and D = decode CPU ms/frame, both UNMEASURED): with T=4,D=20 the synchronous path delivers 544/600/682 KB/s at 5/6/8 Mbps against a 1024 KB/s device ceiling and runs late; the helper delivers 629/754/1004 KB/s with no late frames. With T=3,D=10 there is no difference. So the patch helps only if the device is fast enough and idle time is the bottleneck; if the patched mx4sio_bd (8-sector batches, CMD18/CMD12 per batch, 100 us polling watchdog) is itself below the stream bitrate, no EE-side change will fix it. That ceiling is unmeasured — a DIAG `[sms-io]` capture from the reporter (bytes / read_ms on MX4SIO) would settle it.

RULED OUT as EE-side causes of the residual USB "slight slowdown" (by code reading, not measurement): helper priority (62 > all player threads, CPU per slot is one cache write-back + one RPC); slot count vs buffer (192/64 = exactly 3, 2 MB packet queue is the real cushion); semaphore handoff (reader wake-up delay no longer stalls the IOP); memcpy (same single copy as rev4); cache flushes; the 8 ms timer (DIAG-only sampling, not in release builds); byte-wise parsing (payloads are bulk memcpy, header bytes are inline with a function call only at refill). `File_Skip` for skips < 64 KiB reads 512 bytes at a time into a scratch buffer — pre-existing upstream behaviour, negligible, not worth touching.

UNVERIFIED HYPOTHESES for the residual USB gap (not findings, do not present as causes):
(a) IOP stack: legacy SMSUMS always issued 32 KiB sector-aligned SCSI reads through its own block cache; the fork's bdmfs_fatfs clips each read at a cluster boundary and filexio caps at its 16 KiB rwbuf, so a FAT32 stick with 4 KiB clusters gets 4 KiB SCSI commands with per-command CBW/CSW overhead on USB 1.1. Cheap reporter check: cluster size of the stick, or reformat with 32 KiB allocation units.
(b) Cushion drain: a 20-25% throughput deficit empties the 2 MB packet pre-buffer in ~10-13 s, which fits a slowdown confined to "seconds 10-16" if that stretch is a bitrate peak (see finding 2).
