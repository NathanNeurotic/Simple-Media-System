# i10-mp4-stall

Issue #10 (HandBrake MPEG-4 .mp4 on USB: slow open, 7 s of playback, then frozen video + looping audio) investigated on the host only. No PS2/emulator run; nothing here is hardware-accepted. Repository untouched (git status identical to start); all work is in (investigator scratch, not kept)/i10-mp4-stall/h (harness build.py/prefix.h/post.c wrapping the REAL src/SMS_ContainerMOV.c + real SMS_Rescale/CalcPktFields; fixtures from gen.sh; patched trial copies mov_fix1.c, mov_fix3.c, mov_fix4.c; trial.sh/trial3.sh/trial4.sh/ht.sh). HandBrakeCLI was not available, so fixtures are ffmpeg 7.1 files muxed HandBrake-style (libavformat mov muxer, mp42 brand, 90 kHz video timescale, 10 s GOP, moov at end, AAC/MP3, chapters, 23.976/25/29.97/30 fps, with/without B-frames, VFR, trims, delays). The reporter's actual file was never available.

WHAT WAS REPRODUCED
1) Rev1 (v3.0.0-rev1 = 95b803b, the build the reporter tested) reads these files with ONE BACKWARD SEEK PER VIDEO FRAME (2700 backward seeks / 14.7 MB re-read over a 90 s clip; 2250 for 25 fps/44.1 kHz; 1650 with MP3 audio). Cause: rev1 ignored the audio priming edit list, so its DTS order (video first) disagreed with the file's physical order (audio first). In rev1 the USB/fileXio stream path used STIO_Seek (drops the buffer + lseek) followed by STIO_Fill, which synchronously re-reads the whole 196608-byte stream buffer. At USB 1.1 throughput that cannot keep up with real time, so the pre-filled packet queues drain and playback starves: this is the mechanism most consistent with "plays ~7 s, then video freezes and audio loops", and with the issue title "Stuttering". It is a hypothesis, not proof: it depends on the reporter's file having the same A/V start layout as ffmpeg's muxer output, which could not be checked (confidence ~0.4 that this is the reported freeze).
2) Current master (c275476) no longer does that on these fixtures (edit-list timeline from 59d0ed1), but 8 of 17 playable fixtures still take 42-111 backward seeks per 90 s because the interleave key is rounded to milliseconds. A one-condition fix (prefer lower file offset when DTS are within 1 s) brings every fixture to 0 backward seeks.
3) Video esds is never parsed on master or rev1 (stsd video entry read 2 bytes short), so the MPEG-4 VOL seed added by 99b1b5f has never executed for any MP4. One-line fix verified on host.
4) Master rejects whole files that rev1 opened (over-strict edit-list gate from 59d0ed1): AAC with 2048/2112-sample priming, zero last stts delta, start/tail trims.

RULED OUT / NOT REPRODUCED
- "Playback began at 0:28": no fixture can start anywhere but 0 (video first PTS 0, audio -21..-25 ms, or the intended +/-1.5 s on delay fixtures). Possible benign explanations: stopwatch/recording time after the 10-20 s load, or the history "Resume" prompt. Unexplained.
- The exact 0:35 freeze with looping audio was not reproduced (needs hardware).
- Not the cause on the tested fixtures: chapter 'text' track (skipped, no I/O), moov-at-end vs faststart (both open), 32-bit timestamp overflow for short clips (none; rev1's 32-bit DTS*TimeRate is safe below ~13 h at 90 kHz), index growth (16 bytes/sample), AAC sample-rate handling, MP3-in-MP4 (esds object type 107 maps to MP3), divide-by-zero in SMSContainer_CalcPktFields when audio bitrate is 0 (build uses -mno-check-zero-division, so no trap; only a garbage packet duration).
- Known limitations seen but not #10: 'ac-3' sample entry is unmapped (video plays silent); sample offsets above 4 GiB are truncated to uint32 in the MOV index; seeking lands on keyframes, i.e. up to 10 s early with HandBrake's 10 s GOP.

CHANGES ON MASTER AFTER THE REPORTER'S TEST (all await reporter retest; none hardware-verified by me): 234c787 File_Skip seeks for skips >= 64 KiB (the slow-open fix, PR #30); 2a9a578 MOV table bounds; d1b7291 deeper BDM stream buffer; 3c2fcba and 1422165 bounded synchronous BDM/USB refills; 0033b80 async read validation; 8a25e22 read-ahead on confirmed USB; 2a3dadf, 4cfc776, 5f4fcb5, db210e1 MOV packet timing/index/co64/stts hardening; 59d0ed1 edit-list timeline (m_TimeOffset/m_DTSShift), which is what removed the per-frame backward seek; 632c990 sample-size payload checks; c275476 scrollbar seek. Note 99b1b5f (MPEG-4 esds seed) was already in rev1 but is dead code until finding 1 is fixed.

Suggested order: finding 1 and finding 2 are one-line changes in src/SMS_ContainerMOV.c that pass the four existing MOV host tests unchanged; finding 3 is an owner decision; 4 and 5 are low priority. Then ask the reporter to retest and, if it still fails, to attach the file or a MediaInfo dump (frame rate, audio rate, B-frames, encoder).
> Review note: the first proposed fix (skip the two-byte colour-table ID) is historical: src/SMS_ContainerMOV.c on the branch head already does it, so do not add it again. The same applies to the matching note in i22-converter.md.

## #1 MP4 video esds is never parsed: stsd video entry is read 2 bytes short, so the MPEG-4 VOL seed never runs
- issue: 10
- severity: high
- category: bug
- files: ['src/SMS_ContainerMOV.c', 'src/SMS_MPEG4.c', 'tools/test_mov_parser.py']
- reproduced: True
- confidence: 0.9
- risk: The fix makes the VOL seed run on a PS2 for the first time. Expected effects: low_delay=1 from the VOL makes no-B-frame files output the current picture instead of the previous one (one frame earlier), and VOL width/height overwrite the stsd values (the seed comment says this is intended). A corrupt esds would now reach Codec_MPEG4_DecodeHeader, same exposure as an in-band VOL in AVI. Decoder behaviour after the fix is unverified on hardware.

### evidence
_mov_read_stsd video branch (src/SMS_ContainerMOV.c lines 343-348) consumes 16+2+2+46+2 = 68 bytes after the 16-byte entry header, i.e. 84 of the 86-byte VisualSampleEntry; the trailing pre_defined/colour-table-id (0xFFFF) is left unread. _mov_read_dflt then reads a child size of 0xFFFF00xx, hits the size guard and breaks, so the 'esds' child is never dispatched. Host run of the real parser on 20 ffmpeg-muxed HandBrake-style files: every video stream reports br=0 extradata=0 (audio reports extradata=5), on current master and on rev1. Byte check of a fixture: samples contain only GOV (0x1B3) + VOP (0x1B6); the VOL (0x120) exists only in esds (0 in-band VOL start codes in mdat). Consequence by code reading: the seed in MPEG4_Init (src/SMS_MPEG4.c lines 714-717, commit 99b1b5f, whose own comment says it fixes MP4-muxed mp4v) has never executed for MP4. The decoder runs on defaults: m_TimeIncRes forced to 1 and m_TimeIncBits guessed (_decode_vop_header 2570-2585), low_delay unknown, and VOL-only tools (quarter-pel, MPEG quant matrices, interlace, data partitioning) silently ignored. A plain no-B-frame progressive file still decodes because the guess is right when the first VOP has time increment 0, so this is NOT shown to be the cause of the #10 freeze; B-frame files get wrong m_PPTime/m_PBTime at every one-second boundary (B-VOPs skipped or mis-predicted) and qpel/MPEG-quant/interlaced files garble.

### fix
In _mov_read_stsd, video branch, directly after `lpCodecCtx -> m_BitsPerSample = File_GetShortBE ( apFileCtx );` (line 348) add one line: `File_Skip ( apFileCtx, 2 );` (colour table id). Trialled in a private copy (scratch h/mov_fix1.c): all fixtures then report video br=1.19-1.21 Mbit/s and extradata=47/48 bytes, codec ID stays MPEG4 (esds object type 32 is in s_MP4ObjType), packet output is byte-for-byte unchanged, the audio-only M4A path still opens the same files, and tools/test_mov_parser.py, test_mov_packets.py, test_mov_index.py, test_mov_sample_sizes.py all pass with --source pointing at the patched copy.

### test
Extend the video-trak fixture in tools/test_mov_parser.py with a full 86-byte VisualSampleEntry carrying an esds child and assert the video stream ends with m_ID == SMS_CodecID_MPEG4, m_BitRate > 0 and m_UserDataLen equal to the DecoderSpecificInfo length (fails on current master, passes with the fix). On hardware: play a HandBrake MPEG-4 MP4 with and without B-frames.

## #2 MOV packet interleave is chosen by millisecond-rounded DTS only, causing backward seeks that restart USB read-ahead (every video frame in Rev1, 0.5-1.2 per second on master)
- issue: 10
- severity: medium
- category: perf
- files: ['src/SMS_ContainerMOV.c', 'src/SMS_FileContext.c']
- reproduced: True
- confidence: 0.8
- risk: Read order within a 1 s window now follows the muxer's interleave instead of strict DTS, so a badly interleaved file can deliver up to 1 s of one stream before the other; the player queues already absorb this for AVI. Truly non-interleaved files behave as before. Host-verified only; the USB cost model comes from reading SMS_FileContext.c, not from a console measurement.

### evidence
_ReadPacket (src/SMS_ContainerMOV.c lines 1233-1249) picks the stream with the lowest DTS rescaled to SMS_TIME_BASE (1 ms) and ignores file position. Whenever that order disagrees with the physical order it calls lpFileCtx->Seek backwards (line 1268). Host counts with the real reader over 90 s clips. Rev1 source: 2700 backward seeks (one per video frame, 14.7 MB re-read, max 20 KB back) on 30 fps/48 kHz AAC, 2250 on 25 fps/44.1 kHz, 1650 with MP3. Current master: 0 on 30 fps/48 kHz, but 47 on 23.976 fps, 45 on 25 fps/44.1 kHz, 59 on 29.97 fps, 42 on 30 fps/44.1 kHz MP3, 111 on an audio-delay file. Cost per backward seek: rev1 fileXio path = STIO_Seek drops the buffer, next STIO_Fill synchronously re-reads the full 196608-byte buffer (m_StreamSize 384 >> 3 blocks); master = STIO_SeekPf/STIO_Stream stops prefetch, seeks, restarts it and waits for the first slot. The rev1 per-frame case cannot keep up on USB 1.1 and is the mechanism most consistent with the reported freeze after the pre-filled queues drain, but that link is inferred, not observed. Raising the key to microseconds (scratch h/mov_fix2.c) fixed most files but made the audio-delay file worse (166), so resolution alone is not the right fix.

### fix
One condition in _ReadPacket: replace `if ( lDTS < lBestDTS ) {` with `if ( !lpSample || ( lDTS - lBestDTS < SMS_TIME_BASE && lBestDTS - lDTS < SMS_TIME_BASE ? lpCurSample -> m_Pos < lpSample -> m_Pos : lDTS < lBestDTS ) ) {` i.e. when two candidates are within 1 s, take the one stored first in the file, otherwise keep DTS order (same rule libavformat's mov demuxer uses on seekable input; AVI in SMS already reads in pure file order). Trialled in scratch h/mov_fix3.c: 0 backward seeks on all 17 playable fixtures, identical per-stream packet counts and first/last PTS, seek-to-45 s output identical, and all four tools/test_mov_*.py tests pass against the patched copy.

### test
Add a case to tools/test_mov_packets.py with two streams whose physical order is A,V but whose rounded DTS are equal or 1 ms inverted, counting Seek calls in the harness FileContext: expect 0 backward seeks; plus a non-interleaved case (streams more than 1 s apart) asserting DTS order is still used.

## #5 PAL 2:2 pulldown forces the video time base to 1/25, which is wrong for MP4 video whose time base is not one frame per tick
- issue: 10
- severity: low
- category: bug
- files: ['src/SMS_Player.c']
- reproduced: False
- confidence: 0.45
- risk: Touches an opt-in PAL-only path used by AVI playback; the skip variant leaves AVI behaviour bit-identical. Unverified on hardware and not reproduced on host.

### evidence
Code reading only. _setup_video_pulldown22 (src/SMS_Player.c lines 1574-1650) runs when SMS_PF_PDW22 is enabled (opt-in, not in the default m_PlayerFlags), the display is PAL or 576p, and the frame rate is between 23.8 and 25 fps; it calls SMSContainer_SetPTSInfo ( lpVideoStm, 1, 25 ) at line 1593. That is valid for AVI, where one tick is one frame. For MP4 the host harness shows a HandBrake-style 23.976 fps track at tb=1/90000 (frame durations alternate 3753/3754, so the reader cannot reduce it to frame units); after the override each 90 kHz tick would be read as 1/25 s, putting video PTS thousands of times ahead of audio, so the VBlank handler would hold the picture and _Seek positions would be wrong. The reporter's console is PAL, but the option is off by default and this would freeze on the first frame rather than after 7 s, so it does not match the report well.

### fix
Scale the existing video time base instead of replacing it, using the same ratio the audio loop below already applies: new Num/Den = old Num * lRate / ( old Den * lBase * 25 ) reduced (for AVI this is exactly 1/25), or simply skip the pulldown when lpVideoStm -> m_TimeBase.m_Num * lRate != lpVideoStm -> m_TimeBase.m_Den * lBase (time base is not one frame per tick). The skip variant is one condition.
