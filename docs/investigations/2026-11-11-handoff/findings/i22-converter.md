# i22-converter

Issue #22 / converter investigation (read-only; all experiments in (investigator scratch, not kept)/i22-converter/). No PS2 hardware or emulator was used; nothing here is a hardware-acceptance claim.

WHAT WAS RUN
- Converter suite on Windows (Python 3.14, PySide6 6.11, ffmpeg 9.0.2): test_converter 35 OK, test_multitrack 12 OK, test_geometry 7 OK, test_file_size 6 OK, test_end_to_end all 10 presets OK. tools/test_converter_publication.py timed out (30 s Git Bash step on a busy machine) - judged environmental, it is a CI-workflow test, not re-run.
- Real ffmpeg conversions of 14 synthetic sources (1080p BT.709, full-range H.264/HEVC/VP9, 720p 23.976 + AC-3 5.1, 24-bit/96 kHz FLAC, PAL anamorphic interlaced MPEG-2, 2-audio + 2-subtitle MKV, cover-art MP3, 853x481 yuv444p 60 fps mono, silent 320x240) through every preset using the real build_ffmpeg_cmd + AdvancedSettingsWidget + validate_converted_file, then ffprobe; plus every codec choice the Advanced Settings widget offers per container.
- Converter MP4 outputs were fed to the REAL src/SMS_ContainerMOV.c + REAL SMS_CodecGetID tables compiled on host (gcc, ASan/UBSan, WSL) to see which codec ID the player would assign.

REAL DEFECTS FOUND (details in findings)
1. Player MOV parser never reads the video esds (2 bytes short in the video sample entry) -> MPEG-4 VOL extradata never reaches the decoder; MPEG-1/2-in-MP4 is misidentified as MPEG-4. Reproduced on host with real converter files; one-line fix verified on a private copy. Pre-existing upstream (2.9rev4) defect, not a fork regression. Bears on #10 only as a hypothesis.
2. Converter offers container/codec combinations the player cannot decode or ffmpeg cannot write: AC-3 in MP4/M4A (no codec tag match), Vorbis in MP4 (fails on ffmpeg 9.0.2), MPEG-1/2 video in MP4 (see 1).
3. FLAC preset emits >2-channel and 24-bit files; player FLAC container rejects >2 channels; validator says PASS.
4. Colour: BT.709 sources are not converted to BT.601 (measured error, low severity; explicitly NOT the cause of #20/#23).
5. Dead/duplicated code that can be deleted.

RULED OUT / CONFIRMED OK
- All 10 presets convert and validate for all source types above. GOP: -g 15 for MPEG-1/2 presets, -g 50 default, -g 6 for High-Quality; -bf 0 everywhere.
- Issue #22 features work on host: multi-audio keep-all-tracks, external + embedded text-subtitle burn-in, keep-source-SD (720x576 anamorphic stays 720x576, SAR 64:45), High-Quality preset (PCM, 10 Mbps). Subtitle-path escaping passes its unit tests; a real Windows drive-letter/apostrophe path burn-in was not separately exercised beyond the existing tests.
- The reporter crash-log failure in #20/#23 (psx-place, `-c:v libxvid -vtag XVID ... -f mp4`) is fixed: -vtag is now only emitted for .avi; Xvid + MP4 produces 'mp4v'/OTI 32. The #20/#23 logs otherwise show successful conversions - the converter did not fail there.
- Full-range sources are correctly compressed to limited range with no extra flags (Y 16-21..235-237 on ffmpeg 9.0.2 and 7.1.4).
- AVI codec tags written by ffmpeg (XVID/FMP4/MP43, MP3 0x55, AAC 0xFF, MP2 0x50, AC-3 0x2000, PCM 0x1) all exist in src/SMS_Codec.c. MP4 MP3 (OTI 107) and AAC (OTI 64) resolve correctly.
- MPEG-1 ffprobe oddities (bit_rate 104857200, r_frame_rate 60/1) are VBR-marker/probe artefacts, not defects.
- Size cap (2 GiB - 1, 10 MiB abort headroom) logic covered by test_file_size; AVI >1 GiB uses OpenDML (RIFF AVIX), which src/SMS_ContainerAVI.c handles (AVIX probe, _LoadODMLIdx, m_RiffEndList[8]) - code reading only.
- conv.py audio-only presets failing on a silent source is expected (the worker pre-checks _has_audio()).

## #1 MOV/MP4 parser skips 2 bytes too few in the video sample entry, so the video esds is never parsed (no VOL for MPEG-4, MPEG-1/2-in-MP4 misidentified)
- issue: 10
- severity: high
- category: bug
- files: ['src/SMS_ContainerMOV.c', 'src/SMS_MPEG4.c', 'tools/test_mov_parser.py']
- reproduced: True
- confidence: 0.9
- risk: Enables the esds-seeding path in SMS_MPEG4.c (Codec_MPEG4_DecodeHeader on extradata) that has never executed for MP4 on hardware, and makes MPEG-1/2-in-MP4 route to the MPEG-1/2 decoder for the first time. Host-verified parse only; needs a hardware playback check of an ordinary MPEG-4 MP4 before release. QuickTime sample entries with a real colour table (depth 1-8 bpp palettised) are not handled either way.

### evidence
_mov_read_stsd video branch (src/SMS_ContainerMOV.c ~343-349) reads width/height, skips 46, reads the 2-byte depth, and then hands the remainder to _mov_read_dflt without skipping the 2-byte colour-table-id/pre_defined field. Hex of a converter output (scratch outm/m016.mp4): depth@82 = 0018, colour-table-id@84 = ffff, child box @86 = 00 00 00 5c 'esds'. _mov_read_dflt therefore reads a child size of 0xFFFF0000|.. and bails at its `lAtom.m_Size > apAtom->m_Size - lTotalSize` check, so _mov_read_esds is never dispatched for video. Host harness (scratch movid.py: real SMS_ContainerMOV.c + real SMS_CodecGetID tables, gcc ASan/UBSan) on current source: every converter MP4 prints `video tag='mp4v' [udlen=0 bitrate=0] -> MPEG4`, including an MPEG-2-in-MP4 file (esds OTI 97) and an MPEG-1-in-MP4 file (OTI 106). ffmpeg-written MP4s carry the MPEG-4 VOL only in esds (0 samples with an in-band VOL startcode; first sample starts 000001b6), so SMS_MPEG4.c:696-717, which seeds the decoder from m_pUserData, never runs and the decoder guesses the time-increment width. With a one-line private patch the same harness prints `udlen=43 bitrate=1537284 -> MPEG4`, `-> MPEG2`, `-> MPEG1`, and tools/test_mov_parser.py passes all cases on the patched copy. The identical code is in upstream ps2homebrew/SMS 2.9rev4, so this is an inherited defect, not a fork regression. Any link to issue #10's symptoms (starts at 0:28, stalls) is a hypothesis only.

### fix
In _mov_read_stsd, video branch, immediately after `lpCodecCtx -> m_BitsPerSample = File_GetShortBE ( apFileCtx );` add `File_Skip ( apFileCtx, 2 );  /* colour table id */`. Nothing else.

### test
Extend tools/test_mov_parser.py: for the standard MP4 fixture (mp4v video sample entry with esds) assert the video stream has m_UserDataLen > 0 and m_BitRate > 0, and add one case with esds OTI 0x61 asserting the stream ID becomes MPEG2. Fails before the one-line change, passes after.

## #2 Converter offers MP4/M4A codec combinations the player cannot decode or ffmpeg cannot write (AC-3, Vorbis, MPEG-1/2 video)

- severity: medium

## #3 FLAC preset emits multichannel and 24-bit files; player rejects >2-channel FLAC and outputs 16-bit anyway; validator says PASS
- issue: 0
- severity: medium
- category: bug
- files: ['tools/sms_converter/ffmpeg_utils.py', 'tools/sms_converter/config.py', 'tools/sms_converter/validator.py', 'src/SMS_ContainerFLAC.c']
- reproduced: True
- confidence: 0.8
- risk: Genuine 24-bit sources are reduced to 16-bit in the file (the PS2 output is 16-bit regardless, so no audible loss on target). Sample rate is left untouched; 96 kHz playback on the PS2 audio path is unverified either way. Player rejection of 6-channel FLAC is from code reading of SMS_ContainerFLAC.c, not a hardware run.

### evidence
FLAC preset has sample_rate=None, channels=None, so build_ffmpeg_cmd emits no -ac/-ar/-sample_fmt. Real conversions: AC-3 5.1 source -> 6-channel FLAC, validator PASS; src/SMS_ContainerFLAC.c opens a file only when `lData.m_Info.m_nChannels < 3`, so that output will not open. Any lossy/float source (MP3, AAC, AC-3) -> ffmpeg picks s32 (24-bit) FLAC: music.mp3 -> 4,154,277 bytes vs 2,799,655 bytes with 16-bit (+48%), while SMS_FLAC.c reduces every sample to 16-bit on output (`(x << (24-bps)) >> 8`). docs/converter.html already states the FLAC path 'requires mono/stereo and outputs 16-bit PCM' but nothing enforces it. Tested minimal change: adding audio filter `aformat=sample_fmts=s16:channel_layouts=mono|stereo` gives stereo->stereo s16, 5.1->stereo s16, mono->mono s16, size 2,799,655.

### fix
In build_ffmpeg_cmd audio section, when acodec == 'flac' add `aformat=sample_fmts=s16:channel_layouts=mono|stereo` to the audio filter chain; build one comma-joined `-af` string so it combines with the existing optional `loudnorm` (currently `-filter:a loudnorm`) instead of emitting two filter options. No new settings or UI.

### test
Add to test_converter.py: build_ffmpeg_cmd with the FLAC preset contains exactly one audio-filter option and it includes `sample_fmts=s16` and `channel_layouts=mono|stereo`; with normalize_audio=True the same single option also contains `loudnorm`. Optionally an end-to-end case in test_end_to_end.py converting a 5.1 source and asserting channels <= 2 via ffprobe.
