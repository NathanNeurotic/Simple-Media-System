# i24-pause-seek-freeze

Verdict on c275476 (PR #51) for the issue #24 pause -> seek backward -> resume freeze: NOT PROVEN, awaits reporter retest. No console or emulator was available; nothing here is a hardware result.

What landed on master after the reporter's last test (8a25e22, 2026-11-01): the only playback-relevant change is c275476 (PR #51). It touches src/SMS_PlayerControl.c (InitQueues(0) moved before the MPEG reset/seek in PlayerControl_ScrollBar; a failed container seek now returns 0; lDir became +1 for forward seeks; OSD repaint and initial cursor rounding) and adds one line to src/SMS_Player.c (m_EOF = 0, a field nothing reads, so no effect). src/SMS_FileContext.c and the containers are unchanged since 8a25e22. The other commits in that range (#50 720p width, #52 artwork sidecars, #53 poster list) do not touch playback. All of c275476 therefore awaits reporter retest.

What c275476 does and does not establish (code reading):
- The only seek reachable while paused is the SELECT scrollbar; the plain pause loop has no seek. The reporter's file is MPEG-2 PS.
- It closes two code-evident hazards present at 8a25e22: (1) workers were alive while main reset MPEG/IPU state and seeked; (2) a failed container seek left retVal == 1 after InitQueues(0) had terminated every worker, so the player "resumed" with no workers and a frozen picture.
- Hazard (2) is unlikely to be the reporter's case: a host replay of 23 scrollbar seeks (backward and forward, cells 0..32) on a real 59 MB MPEG-2 PS file all succeeded, on both the USB read-ahead path and the 4 KiB synchronous path.
- No backward-specific mechanism was found. Whether the reorder cures the freeze cannot be shown on a host.

Ruled out on host (real src/SMS_FileContext.c STIO code plus real src/SMS_ContainerMPEG_PS.c, ffmpeg-generated 100 s 4.5 Mbit/s MPEG-2 + MP2 file): the scrollbar sequence Stream(pos,0) -> Seek -> Stream(pos,48) -> ReadPacket. Every seek landed within 0.25 s of target, the read-ahead helper restarted exactly once per seek (pf=1), and 400 packets after each seek read with byte-exact audio payloads. UDPFS and the legacy fio double-buffer path were not exercised. Baseline tests pass unchanged: test_player_scrollbar_seek.py, test_player_video_drain.py, test_stio_usb_readahead.py, test_mov_packets.py, test_mpeg_ps_probe.py.

Remaining defects are in findings: two reproduced on host (rewind near the start exits playback; forward scrollbar seek regression from c275476 on AVI/MP4), one reproduced at container level (MPEG-PS seek lands on non-I pictures), one from code reading only (stale pause semaphores).

Unverified lead, not a finding: STIO seeks through 32-bit fileXioLseek. ps2sdk master's bdmfs_fatfs fs_lseek sign-extends the int offset to 64 bits and FatFs clamps a read-mode seek past EOF to the file size, so any seek to an offset of 2 GiB or more would land at EOF. The shipped irx/bdmfs_fatfs.irx is a prebuilt binary whose version I did not check.

## #1 Rewind (LEFT) near or down to the start of a file exits playback instead of restarting from the beginning
- issue: 24
- severity: medium
- category: bug
- files: ['src/SMS_PlayerControl.c']
- reproduced: True
- confidence: 0.85
- risk: Changes the rewind end condition for every container; not hardware-tested. Containers with m_StartTime == 0 behave as before except that the first step is clamped and reaching the start restarts at the sought keyframe instead of offset 0 or a stale offset. A rewind pressed within one step of the start now restarts the file immediately without showing a scan frame.

### evidence
PlayerControl_Scroll (src/SMS_PlayerControl.c:619-822), inherited from upstream. Line 652 does `lTime += lIncr` (-24000 ms for MPEG-1/2, -3000 ms otherwise) with no clamp. The in-loop clamp (787) and the terminal test (675) use 0, but the seek target is `lTime - lpCont->m_StartTime` (667), so with a non-zero start time even lTime == 0 gives a negative lPos that is cast to uint32_t.

Host replay with real STIO + real MPEG-PS container on an ffmpeg MPEG-2 PS file (start time 529 ms):
- LEFT at 12.78 s: iter 1 lTime -11220 ms, aPos 0xFFEFDD7E, container Seek = 0, Scroll returns 0. _Rew_AV returns 0, so _sms_play sets STOP|USER_STOP and exits (SMS_Player.c:1303-1306).
- LEFT at 40.58 s: iter 1 seeks to 16.58 s correctly; iter 2 clamps lTime to 0, aPos 0xFFFF4606, Seek = 0, playback exits.
- Same result on the USB path and the 4 KiB synchronous path.

The failed STIO_Seek keeps the buffered cursor while the descriptor is left at EOF (devpos = file size). That lseek model (clamp to size) matches ps2sdk master bdmfs_fatfs fs_lseek64 + FatFs f_lseek; the shipped irx version was not checked. Under an alternative model where lseek errors without moving, playback continues but does not rewind: it restarts at the stale lFilePos near 12.9 s.

AVI, real _Seek: aPos 0xFFFFFFE7 with aDir -1 returns 0 (`aPos >= m_nIdx`), so LEFT within the first 3 s also exits. MOV has the same range check at SMS_ContainerMOV.c:1371 (not run).

The EE float-to-unsigned saturation in the PS _Seek was emulated in the harness.

### fix
In PlayerControl_Scroll:
1. After line 652 (`lTime += lIncr;`) add `if ( lTime < lpCont -> m_StartTime ) lTime = lpCont -> m_StartTime;`.
2. Lines 670-686: keep the `if ( !lSize ) { retVal = 0; break; }` branch, then set `lFilePos = lpFileCtx -> m_CurPos;` immediately after it, and change the terminal test from `lTime == 0LL` to `lTime == lpCont -> m_StartTime`. Drop the later duplicate assignment at line 686. This also fixes the restart position being 0 or stale when the start is reached.
3. Line 787: `if ( lTime < lpCont -> m_StartTime ) lTime = lpCont -> m_StartTime;`.

Host replay of the patched sequence: iter 1 lTime 529 ms, aPos 0, Seek succeeds, restart at file position 0, 400 packets read, first video PTS 540 ms, on both storage paths and both lseek models.

### test
New host test that extracts PlayerControl_Scroll the way tools/test_player_scrollbar_seek.py extracts PlayerControl_ScrollBar. With m_StartTime = 529, MPEG codec ID and m_VideoTime = 12780, a recording Seek stub must see aPos == 0 on the first call, the function must return 1, and both restart Stream() calls must use the m_CurPos left by that Seek. Second case from 40580 ms: the last Seek must be aPos == 0, never a value >= 0x80000000. Optionally promote the scratch psseek.py replay (real STIO + real PS container) using a synthetic PES stream like test_mpeg_ps_probe.py builds.

## #2 c275476 regression: forward scrollbar seek on AVI/MP4 stops playback when no keyframe exists at or after the target
- issue: 24
- severity: medium
- category: bug
- files: ['src/SMS_PlayerControl.c', 'tools/test_player_scrollbar_seek.py']
- reproduced: True
- confidence: 0.9
- risk: Low. Only the failure path of a forward seek changes. On MPEG-PS a forward seek that failed (target past the last GOP) is retried once and fails again after re-scanning the file tail, then stops as today.

### evidence
c275476 changed PlayerControl_ScrollBar (src/SMS_PlayerControl.c:1346) from an effective lDir = -1 to `lDir = lTime > ( m_VideoTime - m_StartTime ) ? 1 : -1`. Before, lPassTime was assigned lTime every loop pass, so `lTime - lPassTime` was always 0 and lDir was always -1. The same commit made a failed Seek return 0, which stops playback (SMS_Player.c:1222-1225).

AVI _Seek (SMS_ContainerAVI.c:1116-1118) walks forward to m_nIdx and returns 0 when no later keyframe exists. MOV does the same (SMS_ContainerMOV.c:1375-1379).

Host run of the real AVI _Seek on a 60 s, 25 fps index with a 300-frame keyframe interval: scrollbar cells 27..32 return 0 with aDir = +1 and 1 with aDir = -1 (keyframe 1200). The existing tools/test_mov_packets.py already asserts `_Seek(&container,0,1,21)==0` for MOV.

So on short clips or sparse-keyframe files, jumping to the last cells now exits to the browser; at 8a25e22 it seeked to the previous keyframe and played. MPEG-PS ignores aDir and is unaffected.

### fix
Keep the forward preference but fall back to the previous keyframe. In PlayerControl_ScrollBar replace
`if (  lpCont -> Seek ( lpCont, s_Player.m_VideoIdx, lDir, lPos )  ) {`
with
`if (  lpCont -> Seek ( lpCont, s_Player.m_VideoIdx, lDir, lPos ) || (  lDir > 0 && lpCont -> Seek ( lpCont, s_Player.m_VideoIdx, -1, lPos )  )  ) {`.
AVI and MOV _Seek return before mutating any cursor on this failure, so the retry is safe. A simpler alternative is to restore lDir = -1 unconditionally (upstream behaviour).

### test
Extend tools/test_player_scrollbar_seek.py with a case where the seek stub returns 0 for dir == +1 and 1 for dir == -1: expect return -1 and exactly two seek calls (+1 then -1). The existing 'forward' case (one call, +1) must still pass. Add a small host test of the real AVI _Seek modelled on the scratch aviseek.py: last keyframe before target, aDir +1 returns 0, aDir -1 returns 1.

## #3 MPEG-PS seek accepts non-I pictures: picture_coding_type is read from the wrong bits
- issue: 0
- severity: low
- category: bug
- files: ['src/SMS_ContainerMPEG_PS.c']
- reproduced: True
- confidence: 0.6
- risk: Low. Seeks that used to stop on a bogus match now continue to the next real GOP or I picture, landing up to one GOP later. A stream with neither GOP headers nor I pictures after the target would now fail the seek, which stops playback since c275476.

### evidence
_Seek (src/SMS_ContainerMPEG_PS.c:657-661) tests `(  ( File_GetUInt ( lpFileCtx ) >> 19  ) & 3 ) == 1` after a picture start code. File_GetUInt returns the four bytes little-endian, so bits 19-20 are vbv_delay bits; picture_coding_type sits in bits 11-13. The equivalent seek logic exists in upstream 2.9r4.

Player-visible effect is inferred, not observed: after Reset(RECOVER), _get_next_picture (src/libmpeg.c:673-678) starts output at the first P picture, which would be predicted from pre-seek reference frames until the next I picture.

### fix
In _Seek change the picture test to `(  ( File_GetUInt ( lpFileCtx ) >> 11  ) & 7  ) == 1`.

### test
Add a case to tools/test_mpeg_ps_probe.py: a video PES starting with 00 00 01 00 and a B-type picture header whose vbv_delay bits make the old expression match, followed by a PES with a GOP header (00 00 01 B8). _Seek must leave m_CurPos at the second PES.

## #4 Pause semaphores can keep stale counts after a seek when a renderer was not parked
- issue: 24
- severity: low
- category: bug
- files: ['src/SMS_Player.c']
- reproduced: False
- confidence: 0.45
- risk: Touches the worker shutdown path without hardware verification. PollSema on a zero-count semaphore is non-blocking, and all workers are already stopped at that point, so no wakeup can be lost.

### evidence
Code reading only; inherited from upstream.

_terminate_threads (src/SMS_Player.c:224-230) signals s_SemaPauseAudio whenever PAUSE is set. If the audio renderer was blocked in SMS_RingBufferWait rather than parked (audio output ring empty when SELECT was pressed, so the handshake at 1215 skipped its ack), it exits on STOP without consuming the signal. The count stays 1, so on every later pause the renderer acks and returns from WaitSema(s_SemaPauseAudio) immediately, and audio keeps playing through the pause.

Similarly, the handshake at 1215-1216 (and 1162-1163, 1246-1247) only waits for an ack when the ring count is non-zero. A renderer that receives data after that check still signals s_SemaAckPause, leaving a stale ack that lets the next pause proceed before a thread has parked.

Both need a starved output ring at the moment of pause, which is the condition of the MX4SIO stutter and USB slowdown in this issue. Since c275476 the scrollbar seek terminates workers first, so the stale ack no longer exposes the reset/seek to live workers.

### fix
In _terminate_threads, after the `if ( lThread.status != 0x10 ) { ... }` block (all four workers are stopped there), drain both semaphores: `while ( PollSema ( s_SemaPauseAudio ) >= 0 ); while ( PollSema ( s_SemaAckPause ) >= 0 );`. This only helps the seek path; a stale ack on plain pause/resume without a seek would need the handshake itself changed.

### test
No existing host test models the pause handshake. A shim-based test (tools/ps2_kernel_shim.h pthreads, as test_player_video_drain.py does) could extract _terminate_threads and assert both semaphore counts are 0 afterwards when the audio renderer was blocked on an empty ring with PAUSE set. Real confirmation needs hardware: pause during a starved moment, seek, pause again, and check that audio stops.
