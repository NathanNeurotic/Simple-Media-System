## Findings (benefit order)

### SMS-179 — SMSTCPIP `err_to_errno` maps every error to EIO: the signed/unsigned comparison makes the 11-entry errno table unreachable / Category 6
- **Locations:** macro `iop/SMSTCPIP/src/sockets.c:89-91`; table `iop/SMSTCPIP/src/sockets.c:75-87` (`err_to_errno_table[11]`); signedness source `iop/SMSTCPIP/include/lwip/err.h:39` (`typedef s8_t err_t;`), codes `err.h:43-53`; call sites `iop/SMSTCPIP/src/sockets.c:216, :280, :305, :426` (all via `sock_set_errno`).
- **Problem:** The macro is `( (err) < ( sizeof(err_to_errno_table) / sizeof(int) ) ) ? err_to_errno_table[ -(err) ] : EIO`. The right-hand operand of `<` is a `sizeof` expression — type `size_t`, unsigned. `err` is `err_t` = `s8_t` (signed); in the comparison it is integer-promoted to `int` and then, because the other operand is unsigned, converted to unsigned. Every real error is negative (`ERR_MEM` = −1 … `ERR_USE` = −10), so every real error converts to a value ≥ 0xFFFFFFF6, which is never `< 11`. The conditional therefore always takes the EIO branch for any actual error; only `ERR_OK` (0) ever reaches the table (and correctly gets `table[0]` = 0). The carefully maintained table — ENOMEM, ENOBUFS, ECONNABORTED, ECONNRESET, ESHUTDOWN, ENOTCONN, EINVAL, EIO (for ERR_ARG), EHOSTUNREACH, EADDRINUSE — is dead: unreachable by construction. This settles round 8's checked-clean observation ("`err_to_errno` mapping every error to EIO via a signed/unsigned comparison", `sockets.c:89-91`): the mechanism is exactly that comparison, and the consequence is that every consumer of the sockets layer — in-tree, the SMSSMB client above `lwip_*` — receives EIO for out-of-memory, connection reset, address-in-use, and no-route alike, so no caller can distinguish a retryable resource error from a dead connection. (The defect also hides a latent second one: were the comparison naively "fixed" by casting only the size, a hypothetical positive `err` would index `table[-(err)]` out of bounds — lwIP never returns positive errors, so this is a fix-shape constraint, not a live bug.)
- **Fix:** Make the guard signed-correct in the macro's own terms, e.g. test `err <= 0 && -(err) < 11` (in words: index the table only for the non-positive errors the table covers, EIO otherwise). One expression changes; the table, the call sites, and `sock_set_errno` are untouched.
- **Benefit:** Socket errors become distinguishable again — ENOMEM/ENOBUFS (retry/back-off) vs ECONNRESET/ESHUTDOWN (reconnect) vs EADDRINUSE/EINVAL (caller bug) — for every module using the exported sockets API, and an 11-entry table that exists precisely to carry that information stops being dead weight.
- **Effort:** S · **Risk:** Low (callers currently receive EIO in all cases; any caller that somehow depended on always-EIO was depending on the defect) · **Confidence:** High (READ — typedef, table, macro, and all four call sites line-read; the conversion behaviour is the C standard's usual arithmetic conversions, not implementation guesswork).

### SMS-180 — USBD `initCallbackThread` never checks thread creation and returns success unconditionally; `hcdInit` discards even that — if the callback thread does not exist, no USB transfer completion is ever delivered / Category 6
- **Locations:** `iop/USBD/src/driver.c:239-249` (`initCallbackThread`: `callbackTid = CreateThread(&thread); StartThread(callbackTid, NULL); return 0;`); sole caller `iop/USBD/src/hcd.c:485` (return value ignored, inside the `hcdInit` whose unconditional `return 0` is SMS-162's territory); delivery path that depends on the thread: `iop/USBD/src/driver.c:192-210` (`signalCallbackThreadFunc` ends in `WakeupThread(callbackTid)`) and `:212-237` (`callbackThreadFunc` is the only code that invokes `userCallbackProc`).
- **Problem:** Every USB transfer completion in this stack reaches its driver through one route: the HCD queues the finished IoRequest, `signalCallbackThreadFunc` appends it to the callback list and wakes `callbackTid`, and the callback thread dequeues it and calls the driver's `userCallbackProc`. `initCallbackThread` stores `CreateThread`'s result without testing it: on failure (negative thread id under IOP thread exhaustion) `StartThread` is called on an invalid id, no callback thread exists, and the function still returns 0 — and its only caller ignores the return anyway. From then on the module is resident, endpoints open, transfers can be submitted, and *no completion callback ever fires*: every USB driver above USBD hangs on its first transfer. This is the same false-success family as SMS-162 (USBD HCD arena init) and SMS-169 (SMSMAP `_start`) but a distinct site and mechanism — a third member, in the one thread the whole USBD completion model stands on.
- **Fix:** Test `callbackTid` in `initCallbackThread` and return an error if `CreateThread` (or `StartThread`) fails; propagate that error through `hcdInit` so USBD module start fails visibly instead of presenting a stack that can submit but never complete.
- **Benefit:** Thread exhaustion at USBD load becomes a load failure the EE side can see and retry, not a permanently half-alive USB stack whose drivers all hang silently.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ for the missing checks, the unconditional return, the ignored result, and the callback thread's sole-delivery role; INFERRED only for kernel-call failure modes).

### SMS-181 — USBD exports three stubs that report success while doing nothing: `UsbRegisterAutoloader`, `UsbUnregisterAutoloader`, `UsbChangeThreadPriority` / Category 8
- **Locations:** bodies `iop/USBD/src/interface.c:215-230` (each is a `dbg_printf("… stub")` and `return 0;`); exported at `iop/USBD/src/exports.tab:18-20` (slots 14–16 of the `usbd` export table); declared as real API at `iop/USBD/include/usbd.h:249-251`; success value `iop/USBD/include/usbd.h:204` (`USB_RC_OK` = 0).
- **Problem:** These are not internal helpers — they are published, exported entry points that external IOP driver modules link against, declared in the public header with no hint of their status. A driver that calls `UsbRegisterAutoloader` receives `USB_RC_OK` and reasonably believes USBD will probe it when matching hardware appears without it being resident/registered in the normal way; nothing of the sort ever happens — the function is a print statement. `UsbChangeThreadPriority` likewise confirms a priority change that never occurs. There are no in-tree callers (the consumers are out-of-tree driver modules by design), which is exactly why the lie is invisible from inside this repo: every in-tree reader sees a stub, every out-of-tree caller sees success. Half-finished feature surface presented as finished.
- **Fix:** Make the stubs honest: return a non-zero `USB_RC_*` error so callers can detect the unsupported operation and fall back (the export slots themselves must stay — removing them would renumber the table and break the ABI for every other export). If an autoloader is ever actually wanted, that is a feature to build deliberately, not a return value to fake.
- **Benefit:** External drivers stop building load behaviour on a success that means nothing; the API's contract becomes true at the cost of one return value per stub.
- **Effort:** S · **Risk:** Low (a caller that checks the return gains information; a caller that ignores it behaves as today) · **Confidence:** High (READ — stub bodies, export table, and header declarations all line-read; zero in-tree callers is the repo-wide grep).

### SMS-182 — SMSTCPIP `tcp_next_iss` is fully predictable: fixed seed 6510 plus the deterministic `tcp_ticks` accumulator / Category 6
- **Locations:** `iop/SMSTCPIP/src/tcp.c:909-913` (`static u32_t iss = 6510; iss += tcp_ticks; return iss;`); call sites `iop/SMSTCPIP/src/tcp.c:506` (outgoing connect) and `:822` (listen-side PCB); declaration `iop/SMSTCPIP/include/lwip/tcp.h:425`.
- **Problem:** This settles round 8's second checked-clean observation. The initial sequence number for every TCP connection starts from a compile-time constant (6510, identical on every boot and every unit) and advances only by `tcp_ticks` — the stack's own periodic timer counter, which increments at a fixed rate from stack start. An observer who sees one connection's ISN, or who merely knows approximately when the stack started, can compute the ISN of any subsequent connection to within a tick window; two connections opened in the same tick share the same ISN base entirely. Predictable ISNs are the classic enabler of blind (off-path) data injection and reset against a connection the attacker cannot see. Exposure stated at its exact weight: SMSTCPIP's in-tree use is overwhelmingly as a *client* (SMSSMB connecting out to file servers), so the practical victim is an SMS-initiated connection whose peer an on-LAN attacker impersonates or whose session they pollute — a hostile-LAN scenario, not a remote one, and this stack is not internet-facing in SMS's design. The defect is nevertheless real, costs one small change, and is the same weakness class this audit filed for Launchstation's libsmb2 randomness (LAUNCHSTATION-186): a value the protocol requires to be unpredictable, generated deterministically.
- **Fix:** Stop deriving the sequence from the deterministic accumulator alone: seed the static `iss` once, at first use, from a free-running hardware counter sampled at that moment (IOP timer/CPU count — its phase relative to stack start is not attacker-observable), and advance it per connection from that seeded base. No new subsystem, no stored secret; the change is confined to `tcp_next_iss`.
- **Benefit:** Removes exact off-path ISN computability for SMS's TCP connections; subsequent connections' ISNs are no longer a public function of stack uptime.
- **Effort:** S · **Risk:** Low (ISN generation is internal to the stack; any starting value is protocol-legal) · **Confidence:** READ for the predictability mechanism (fixed seed + deterministic increment, both call sites read); INFERRED for practical exploitability (hostile-LAN positioning required; no in-tree listener workload identified).

## Checked-clean (candidates examined and dissolved, with reasoning)

- **`probeDeviceTree` recursion shape (`driver.c:97-107`):** children are recursed into only when the parent already has a driver; a parent that gains a driver in this pass, or fails its probe, does not have its subtree visited in that pass. Dissolved as unreachable-in-practice in this module's registration order: the only intermediate tree nodes are hubs, and the hub driver is registered inside USBD's own init (`initHubDriver`) before any external driver can call `UsbRegisterDriver` — so by the time any `probeDeviceTree` pass runs for another driver, every hub already has its driver and the recursion path is taken. Devices connected after registration go through `connectNewDevice` (`driver.c:190-204`), which probes every registered driver directly. INFERRED (registration-order reasoning over `hcd.c` init sequence read in round 8); no topology constructible in-tree defeats it.
- **`disconnectDriver` skips the first endpoint (`driver.c:139-156`):** iteration starts at `endpointListStart->next`. Dissolved: the first endpoint is the core-owned default control endpoint, opened by USBD itself (`openDeviceEndpoint` path in `hub.c`), not by the disconnecting driver; full teardown including that endpoint is `flushPort`'s job (`hub.c:348-376`), which does remove from `endpointListStart` unconditionally. Driver-unregister ≠ device death; the asymmetry is the design, consistently applied.
- **`allocHubBuffer` partial reset (`hub.c:68-77`):** only `desc.bDescriptorType` and the two `busyFlag`s are cleared on reuse. Dissolved by field-read tracing within `hub.c`: every other `UsbHub` field read anywhere in the file (`numChildDevices`, `portCounter`, `hubStatusCounter`, `controlEp`, `statusChangeEp`, `desc`, `hubStatus`, `portStatusChange`, `statusChangeInfo`) is written earlier in the `hubDrvConnect`/`hubSetupPorts` sequence than any read of it; the un-reset fields are transfer destinations filled before their callbacks consume them.
- **`hubSetFuncAddressCB` treats any non-`USB_RC_NORESPONSE` result as success (`hub.c:469-486`):** observed, not promoted. No third result code for this control transfer was identified anywhere in the TD-completion path read in rounds 7–8, and inventing a failure mode to file against would violate the no-guessing rule. Recorded here so the observation is not lost; INFERRED unreachability.
- **`fetchConfigDescriptors` silently abandons oversize-descriptor devices (`hub.c:398-401`):** observed, not promoted. The cap is a deliberate fixed resource bound (`usbConfig.maxStaticDescSize`), the abandonment is `dbg_printf`'d, and unplug/replug recovers the port through `flushPort`. A "fix" would be a policy invention (kill vs retry vs larger cap), which is the maintainer's call, not a cleanup. The comment in the code states the behaviour honestly.
- **`UsbTransfer` page-span bound (`interface.c:156`):** the `> 1` page-difference check's correctness depends on OHCI TD page-crossing rules (external specification), not settleable from in-tree evidence. Not promoted.
- **`addTimerCallback` delta-list insertion and `HcInterruptEnable = OHCI_INT_SF` assignment (`hub.c:179-211`):** the delta arithmetic traced correct in both insertion branches; the register assignment is correct because OHCI's `HcInterruptEnable` is write-1-to-enable (a `=` of the desired bit is the idiom, not a clobber). `killEndpoint`'s LUT sweep (`hub.c:216-237`) clears the slot of the TD it actually frees — the correct twin whose existence round 8's SMS-165 was measured against; re-confirmed here.
- **`initHubDriver` (`hub.c:43-63`)** checks its `AllocSysMemory` result and fails cleanly — recorded as the positive contrast inside the same module as SMS-162's unchecked arena allocation.
- **`doRegisterDriver` re-registration guard (`driver.c:110-114`):** the `next || prev` test alone would miss a sole-element driver, but the `drvListStart == drv` test catches exactly that case; combined guard is complete.
- **`hubDrvConnect` return codes skip −7 (`hub.c:625-652`):** cosmetic numbering gap in diagnostic returns; no consumer in-tree distinguishes them. Not a defect.
