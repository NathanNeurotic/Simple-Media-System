## 2. Full reasoning — SMS-072 (WEAKENED, the only non-VERIFIED finding)

**Mechanism (exact).** In `CDDA_Fill` (`src/SMS_FileContext.c:458-528`), when the sector just read is the last (`lNextSector >= m_EndSector`, `:470`) and is not the file's start sector, the available length is set at `:482` to `(apCtx->m_Size + lpPriv->m_pCtx->m_Offset) % 2352`, and `m_Pos` is simultaneously set to `m_Size` (`:472`). When `(m_Size + m_Offset) % 2352 == 0` that length is 0, so `CDDA_Read` (`:426-456`) sees `m_pEnd - m_pPos == 0`, calls `Fill` again, gets the EOF branch (`m_pPos = m_pEnd`), and stops — the final sector's bytes are never delivered through the non-streaming path. `CDDA_FillStm` (`:549-588`) does not share this computation, as filed.

**Filed trace reproduced.** Offset 0, size 4704 (= 2 sectors; script: `(4704+0) % 2352 == 0`; `m_EndSector = start + 4704/2352 + 0 = start+2` per `CDDA_InitFileContextInternal:773`): fill 1 takes the non-last, start-sector branch (`:488-493`) and delivers 2352 B; fill 2 takes the last-sector, non-start branch (`:479-483`) and delivers 0 B. Total delivered 2352 of 4704 — the last 2352 B are silently dropped, exactly as filed. The same loss occurs for any exact-multiple sum with offset, e.g. size 4604 + offset 100 = 4704 (fill 1 delivers 2252 B, fill 2 delivers 0 of the remaining 2352 B).

**Why WEAKENED — the defeating branch the headline omits.** The last-sector code has two sub-branches. When the current sector **is** the start sector (`lpPriv->m_CurrentSector == lpPriv->m_StartSector`, `:474`), the code takes `:476-477`: `m_pPos = buff + m_Offset; m_pEnd = m_pPos + m_Size` — the full size, no modulo. A file that fits in a single sector therefore never loses data even when `(size + offset)` is an exact multiple of 2352: size 2352 / offset 0 delivers all 2352 B, and size 2252 / offset 100 (sum 2352) delivers all 2252 B. The finding's headline ("drops the final sector **whenever** (size + offset) is an exact multiple of 2352") is overbroad for that case.

**Exact surviving trigger.** `(m_Size + m_Offset) % 2352 == 0` **and** the file's last sector is not its start sector — equivalently, the file spans at least two sectors (data length + offset > 2352 with the final sector reached through the non-start branch, including after a `CDDA_Seek` into a multi-sector file) — consumed through the non-streaming `CDDA_Fill` path (probe/header/directory-style reads; the initial `Fill` inside `CDDA_InitFileContextInternal:784` and ordinary `CDDA_Read` use). Under that trigger the full filed impact holds: the final 2352 B are silently dropped and `m_Pos` still reports `m_Size`. The filed one-conditional fix (treat modulo 0 as a full 2352 in the `:482` branch) is unaffected.
