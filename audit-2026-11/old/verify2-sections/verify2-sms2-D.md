## 2. Full reasoning for every non-VERIFIED finding

### SMS-089 — REFUTED (restart markers cannot desynchronise a walk that ends at SOF/SOS)

The code flaw exists only in the abstract: `SMS_ArtworkJPEGSize` (`src/SMS_Artwork.c:54-71`) does assume every marker it *reaches* carries a 2-byte length (`:61-63`, `:71`), and it has no special case for RST0–RST7 (0xD0–0xD7) or TEM (0x01). The finding's claimed consequence — "a baseline JPEG written with a restart interval (DRI) therefore desynchronises the walk … and the walk almost always returns 0 … the artwork silently never loads" — is defeated by the walk's own termination points and by JPEG segment order:

1. **The walk returns before any entropy data.** At `:64-68` it returns the verdict as soon as it reaches SOF0 (0xC0); at `:60` it returns 0 on SOS (0xDA). In a valid JPEG the frame header (SOF) always precedes the scan (SOS), and restart markers exist only *inside* the entropy-coded scan data after SOS. There is therefore no point in a valid file at which this walk is positioned on an RST or TEM marker.
2. **DRI itself is handled correctly.** A restart-interval file announces the interval with a DRI segment (0xDD), which *is* length-bearing (length 4). The walk reads its length at `:61-63` and skips it at `:71`, then proceeds to SOF and returns — exactly as for a file without DRI. The decoder confirms this structure: `src/SMS_JPEG.c:526-533` parses DRI as a length-bearing segment (`_segment` + a 2-byte size), its SOS case at `:534ff` requires a frame to have been parsed already (`!lfFrame … goto end`), and RST markers are recognised (`MK_RST`, `src/SMS_JPEG.c:54`) only in scan processing.
3. **No alternative route to an RST/TEM in the header area exists in-tree.** APPn and other header segments are skipped by their lengths, never scanned byte-by-byte, so marker-like bytes inside a segment payload (e.g. an embedded thumbnail) are never interpreted as markers.

What survives: nothing of the stated user-visible defect. A hand-crafted file that inserted a standalone marker *before* SOF would desynchronise the walk — but such a file is not "a baseline JPEG written with a restart interval", and no evidence was found that the in-tree decoder accepts that placement either (its header loop likewise dispatches on length-bearing segment types). The proposed `continue` for 0xD0–0xD7/0x01 is harmless, but as a fix for valid DRI files it fixes a rejection that does not occur.

### SMS-090 — WEAKENED (the `m_Idx == m_Cnt` write is real and reachable; the NULL / never-prepared state is not)

What is code-proven: `_reset` at `src/SMS_SubtitleContext.c:917-922` unconditionally executes `s_SubCtx.m_pPackets[s_SubCtx.m_Idx].m_Pad[0] |= 0x80000000` with no NULL or range check, while `_display` (`:870-894`) loops only `while (s_SubCtx.m_Idx < s_SubCtx.m_Cnt)` and `_destroy` (`:897-915`) NULL-checks `m_pPackets`. `_display` can indeed leave `m_Idx == m_Cnt`: its loop increments `m_Idx` past each expired packet (`:891`) and exits on the `m_Idx < m_Cnt` condition, so after the last subtitle expires `m_Idx == m_Cnt`. A subsequent Reset then writes one packet past the `calloc(m_Cnt, …)` array allocated in `_produce_packets` (`:716`). The proposed one-line guard remains correct for that state.

What is narrower than the finding states:

- **The "Prepare was never run (load produced no packets) ⇒ `m_pPackets` is NULL" state is not shown reachable, and its parenthetical conflates two different things.** Load producing no packets does not mean Prepare never runs: Prepare is called unconditionally for a non-NULL subtitle context in `_prepare_ipu_context` (`src/SMS_Player.c:181`, invoked at `:1110` before playback), and in that case `m_pPackets` is whatever `calloc(m_Cnt = 0, …)` returns — not demonstrably NULL. Conversely, the error path that could leave a context unprepared sets `s_Player.m_pSubCtx = NULL` (`src/SMS_Player.c:1010`), after which no Reset call site can fire.
- **The caller file is misattributed.** The finding says the seek caller is `SMS_Player.c`; the actual subtitle `Reset()` call sites are all in `src/SMS_PlayerControl.c:774,816,1348`, each guarded only by `if (s_Player.m_pSubCtx)` — none adds an index/NULL guard, so the reachable half of the finding is unaffected by the correction.

Exact narrower truth: subtitle Reset can write one packet past the packet array when it is invoked after `_display` has consumed the last packet (`m_Idx == m_Cnt`, including the degenerate prepared-with-zero-packets case subject to `calloc(0)` semantics); a write through a never-prepared NULL `m_pPackets` was not established as reachable.

### SMS-091 — WEAKENED (unbounded walks in code; out-of-bounds walk unreachable for the sole caller)

What is code-proven: `GUIMenu_ShowItem` (`src/SMS_GUIMenu.c:362-375`) hides with `while ((--m_pFirst)->m_Type & MENU_ITEM_HIDDEN);` (`:369`) and `while ((++m_pLastV)->m_Type & MENU_ITEM_HIDDEN);` (`:371`), with no `m_pItems` floor, no `m_pLast` ceiling, and `aPos` itself unchecked before `&m_pItems[aPos]` (`:365`). As generic menu code the walks are genuinely unbounded, and the proposed two-condition bound is a correct hardening.

Why the claimed out-of-bounds walk does not trigger in-tree: the sole caller is `_pdw22_handler` at `src/SMS_GUIMenuSMS.c:2342`, always with the literal `aPos = 4` on `s_PlayerMenu` (item 4 = SPDIF, item 5 = Pulldown 2:2, defined at `src/SMS_GUIMenuSMS.c:321-327`).

- *Downward walk* (requires `m_pFirst == &items[4]`): the first step lands on item 3, which is never hidden anywhere in the tree — the only `MENU_ITEM_HIDDEN` assignments for this menu are to items 4 and 5 (`src/SMS_GUIMenuSMS.c:966-970` and ShowItem itself on item 4). The loop condition tests the item just stepped onto, sees it visible, and stops after exactly one step.
- *Upward walk* (requires `m_pLastV == &items[4]`): the first step lands on item 5. The handler is only invocable in PAL/576p modes, where the menu setup leaves item 5 visible (`src/SMS_GUIMenuSMS.c:965-967`); in non-PAL modes item 5 is hidden (`:968-970`) but then it cannot be the current item, so its handler — the only path to this call — cannot run. Again the walk stops after one step.

Exact narrower truth: this is a latent unbounded walk in a generic helper, not a reachable out-of-bounds read in the shipped caller/menu configuration; triggering it requires a future caller or menu in which the item adjacent to the hide target, in the walk direction, is itself hidden at the array edge. (This matches the finding's own Low/INFERRED confidence, but its problem text presents the garbage-flag walk as the operative consequence; on the pin it cannot occur.)

### Note on a VERIFIED finding (SMS-081, second half)

The duplicate `GUIDevMenu_RenderSelRect` claim was checked adversarially for a case in which the `:180` call is the *only* one: it fires only when `m_pActRect && m_pActive`. When the device list is non-empty, `m_pActive`/`m_pSelected` are set together on first add (`src/SMS_GUIDevMenu.c:350-351`) and the `:209` call — with the same arguments, after the icon loop has recomputed the offsets the arrow is derived from — overwrites the same `m_pSelRect` packet (`:101-139` writes all 8 qwords). When the list is empty, `m_pActive` is NULL (removal of the last node reassigns it to prev/next, both NULL, at `:410`), so the `:180` guard blocks it. The first call is therefore dead in all reachable cases, as claimed.
