# Sable — SMS Round 7 (scope extension): `iop/` upstream-snapshot trees

- **Repo / pin:** Simple-Media-System at `e65ced39a27eee8d996e9257e21594d1cac1c93d` (verified by `git rev-parse HEAD` this round; `git status` clean before and after; read-only, nothing edited, clone not updated).
- **Scope:** the six `iop/` trees Round 3 inventoried as pristine upstream snapshots (import `d704063`, no local C patches; SMSUMS/USBD Makefile-only changes in 2017): SMSTCPIP, SMSMAP, SMSUMS, USBD, SMSPWROFF, SMSDev9. **Not** re-done, per instructions: smbman-sms, SMSUdpfs local mods, SMSCDVD (Rounds 2–3), SMSSMB (dead, SMS-036, settled).
- **Method:** per tree, first decide whether it parses **external** input (wire packets, disc/FAT structures, USB device-supplied descriptors/responses). If yes, a Category 6 pass on its **parsing entry points only** — not a line audit of the whole tree. If no, the tree stays inventoried with the reasoning stated. Concrete defects only: OOB read/write, unchecked lengths from the wire/disc/device, integer overflow/underflow in length math.
- **Labels:** candidates are labelled TCPIP-n / SMAP-n / UMS-n / USBD-n (**not** SMS-numbered — numbering is the parent's). **READ** = the code chain was read at the cited lines this round. **INFERRED** = reachability/effect that code reading alone cannot settle (hardware behaviour, stale-buffer contents, caller state). Dissolved candidates are listed as checked-clean with the reason they dissolved.
- **Cross-cutting physical-containment fact (READ, used in several dissolutions below):** every received Ethernet frame lands in a **single** `PBUF_POOL` pbuf whose data area is `PBUF_POOL_BUFSIZE` = **1540** bytes (`iop/SMSTCPIP/include/lwipopts.h:63`; pool stride in `iop/SMSTCPIP/src/pbuf.c` `pbuf_init`). Header-field reads a few bytes past a packet's *logical* length therefore stay inside that allocation and read stale pool bytes; those are **not** promoted. What **is** promoted is where a wire/disc/device length is then *trusted* for an unbounded walk, a copy, or a delivery — i.e. where the read/write leaves the allocation or the chain.

## 2. SMSTCPIP — candidates

### TCPIP-1 / IP reassembly trusts the header's total length, not the received chain — `copy_from_pbuf` walks off the end of the chain and dereferences NULL · READ (code chain), INFERRED (exact IOP fault manifestation)

- **Entry / provenance:** wire fragment → `iop/SMSMAP/smap.c:1020` `ps2ip_input` → `iop/SMSTCPIP/src/ip.c:261-264` (fragment flag/offset set → `ip_reass(p)`) → `iop/SMSTCPIP/src/ip_frag.c:143-159` (`ip_reass`).
- **Chain (all READ):**
  1. `ip.c:227-230`: `len = IPH_LEN(iphdr)` (wire u16, byte-swapped); `pbuf_realloc(p, len)`. `pbuf_realloc` is **shrink-only**: `iop/SMSTCPIP/src/pbuf.c:248` — `if (new_len >= p->tot_len) return;`. A fragment whose IP header *claims* more bytes than were received therefore keeps its short, real `tot_len`; nothing anywhere records the discrepancy.
  2. `ip_frag.c:143-151`: `len = IPH_LEN(fraghdr) − IPH_HL(fraghdr)*4`; `offset = (IPH_OFFSET & IP_OFFMASK)*8`; the **only** length guard is `offset > IP_REASS_BUFSIZE || offset + len > IP_REASS_BUFSIZE` (5760) — i.e. the claimed length is checked against the *reassembly buffer*, never against `p->tot_len`.
  3. `ip_frag.c:159`: `copy_from_pbuf(p, &i, &ip_reassbuf[IP_HLEN + offset], len)` with `i = IPH_HL*4`.
  4. `ip_frag.c:67-72` (`copy_from_pbuf`): `for (; len; p = p->next) { l = len < p->len ? len : p->len; mips_memcpy(buffer, p->payload, l); … }` — the loop condition is the *claimed* `len` only; there is **no `p != NULL` check**. A single-pbuf received fragment (the only shape SMSMAP produces) whose claimed `len` exceeds its real `p->len − IPH_HL*4` exhausts the chain, advances `p` to NULL, and the next iteration dereferences `p->len` at `:68`.
- **Trigger shape:** any fragmented IPv4 packet (MF set or offset ≠ 0) addressed to the console whose first-processed fragment overstates `IPH_LEN` — e.g. claims 1,500, actually carries 100. No checksum obstacle beyond the IP header checksum, which the sender computes over the header as sent (`ip.c:222` verifies only `iphdrlen` bytes).
- **Guard presence:** the 5760 check at `:151` is real but answers the wrong question (destination capacity, not source availability). No `len ≤ p->tot_len − IPH_HL*4` check in `ip_input`, `ip_reass`, or `copy_from_pbuf`.
- **Note:** the same helper is used by `ip_frag` (output, `:294`) with internally-derived lengths — not part of this candidate.

### TCPIP-2 / Reassembly bitmap is indexed at 90 when the reassembled length is exactly 5760 — one byte past the 90-byte bitmap · READ

- **Location:** `iop/SMSTCPIP/src/ip_frag.c:89` — `static u8_t ip_reassbitmap[IP_REASS_BUFSIZE / (8*8)]` = `5760/64` = **90** bytes, indices 0–89. Writes/reads at `:174` and `:195`.
- **Chain (READ):** a fragment ending exactly at the buffer limit passes the guard at `:151` (`offset + len > IP_REASS_BUFSIZE` is false for `offset + len == 5760`). In the cross-block branch, `:174` does `ip_reassbitmap[(offset + len)/64] |= ~bitmap_bits[…]` → index **90**, a read-modify-write one byte past the array (the OR operand happens to be `~bitmap_bits[0]` = 0 for this exact length, so the stored value is unchanged — the access itself is still out of bounds). If that fragment completes the packet, `:184` sets `ip_reasslen = 5760` and the completion test at `:195` reads `ip_reassbitmap[ip_reasslen/64]` = `ip_reassbitmap[90]` and compares it against 0 — i.e. reassembly completion for a maximum-size datagram is decided by an adjacent static byte, not by the bitmap.
- **Guard presence:** none — `:151` admits the equality case and no index clamp exists at `:161-174` or `:192-195` (the loop at `:192`, `i < ip_reasslen/64 − 1`, is in-range; only the two endpoint accesses are not).
- **Severity note:** bounded to a 1-byte static-adjacent access; the concrete harms are the OOB access itself and a 5,760-byte datagram that can never complete (or completes on a neighbour byte's value). Not a heap smash; stated as found.

### TCPIP-3 / TCP data-offset (`hdrlen`) is never validated — its `pbuf_header` result is ignored and `p->len`/`tot_len` underflow · READ (code chain), INFERRED (downstream delivery extent)

- **Location:** `iop/SMSTCPIP/src/tcp_in.c:157-158`, on top of `iop/SMSTCPIP/src/pbuf.c:291-317` (`pbuf_header`).
- **Root helper defect (READ):** for `PBUF_FLAG_POOL`/`PBUF_FLAG_RAM` pbufs, `pbuf_header(p, header_size)` with a **negative** (forward) `header_size` only checks that the new payload does not move *before* the pbuf struct (`pbuf.c:299`). It never checks the move against `p->len`. It returns 0 while `p->len += header_size` and `p->tot_len += header_size` (`:312-313`) wrap as u16. The REF/ROM branch at `:304-308` does have a length check — the pool branch, which is the receive path, does not.
- **Chain (READ):**
  1. `tcp_in.c:121`: the *first* header strip is safe — after `pbuf_header(p, −IPH_HL*4)` (bounded by `ip_input`'s `iphdrlen > p->len` drop at `ip.c:217`), the code checks `p->tot_len < sizeof(struct tcp_hdr)` and drops. The TCP checksum at `:138-140` is likewise computed **before** the bad move, over the true `tot_len`, in `iop/SMSTCPIP/src/inet.s` `inet_chksum_pseudo` (which loops per-pbuf over `p->len`) — so a sender who computes a correct checksum over the segment as sent passes cleanly. The checksum is not a mitigation here.
  2. `tcp_in.c:157-158`: `hdrlen = TCPH_HDRLEN(tcphdr)` — the wire data-offset nibble, 0–15, **never** checked against 5 or against the remaining segment length — followed by `pbuf_header(p, −(hdrlen*4))` with the **return value ignored**.
  3. A segment carrying e.g. 20 bytes of TCP (header only) with data-offset 15 moves the payload 60 bytes and sets `p->len`/`p->tot_len` to `20 − 60` mod 2¹⁶ ≈ 65,492. `tcp_in.c:168` derives `tcplen` from that wrapped `tot_len`, and for a matched PCB `tcp_in.c:284` sets `inseg.len = p->tot_len` (the wrapped value) before `tcp_process`/`tcp_receive` treat the segment as ~64 KB of in-window data. A data-offset of 0–4 is likewise accepted (payload left pointing into the TCP header), though the >length case is the memory-relevant one.
- **Guard presence:** none at `:157-158` — no `hdrlen ≥ 5`, no `hdrlen*4 ≤ p->tot_len`, no check of the `pbuf_header` return that the same function *does* honour at `:121`.
- **Related, not separately counted:** `tcp_parseopt` (`tcp_in.c:1161-1201`) walks options bounded only by the same claimed `lLen = TCPH_HDRLEN(tcphdr)` (`:1167, :1173`), reading `opts[c+1..c+3]` up to `(lLen−5)*4` bytes past the real segment when the offset is overstated; its one solid guard is the MSS clamp at `:1185` (`pcb->mss = mss > TCP_MSS ? TCP_MSS : mss`). It is a consequence surface of TCPIP-3, not an independent candidate.

### TCPIP-4 / UDP: a datagram shorter than the UDP header is "stripped" by the same unchecked `pbuf_header` and can be delivered with a ~65 KB length · READ (underflow), INFERRED (delivery — needs a bound PCB and the checksum path below)

- **Location:** `iop/SMSTCPIP/src/udp.c:172` (strip), `:309`/`:341` (restore/strip-again), `:342-344` (delivery); root helper as in TCPIP-3 (`pbuf.c:291-317`).
- **Chain (READ):**
  1. `udp_input` is reached for any IPv4/UDP packet `ip_input` accepts; `ip_input` never requires `IPH_LEN ≥ IPH_HL*4 + UDP_HLEN` (`ip.c:217` checks the IP header length only, `:230` shrink-only realloc — see TCPIP-1).
  2. `udp.c:172`: `if (pbuf_header(p, −((s16_t)(UDP_HLEN + IPH_HL(iphdr)*4)))) { /* drop short packets */ … }`. For a pool pbuf this call **cannot fail** on a forward move (TCPIP-3 root), so the "drop short packets" branch is dead for exactly the packets it names. With IP payload `u < 8` bytes, `p->len`/`p->tot_len` wrap to ≈ 65,528 + u and the payload points past the datagram; `udphdr` at `:182` is then formed at `payload − UDP_HLEN` and the ports at `:186-187` are read from bytes 20–23 of the IP packet (attacker-controlled whenever `u ≥ 4`).
  3. If a PCB matches those ports (or the destination is the console, `:306`), the code restores 8 bytes at `:309`, verifies the checksum over the *restored* (small) length — the assembly checksum loops over `p->len`, `inet.s` `inet_chksum_pseudo` — strips the header again at `:341` (re-wrapping the length), and at `:344` calls `pcb->recv(…, p, …)` with `p->tot_len` ≈ 65,528 + u. The sockets layer then trusts that length: `api_msg.c`/`api_lib.c` account `recv_avail += p->tot_len`, and `lwip_recvfrom` (`sockets.c:346-353`) copies `min(caller_len, netbuf_len)` via `netbuf_copy_partial` (`api_lib.c:82-119`), whose per-pbuf copy length is `p->len − offset` — the wrapped value — so a receiving application can be handed bytes past the received datagram and past the 1540-byte pool buffer.
- **Conditions, stated plainly:** a UDP socket must be bound to the port the short datagram names (SMS's network features do bind UDP sockets in normal use), and the `:326-339` checksum gate must pass — either the (partially stale-buffer) checksum field reads as 0, or the sender solves the pseudo-checksum over the truncated window, all of whose input words except the checksum field itself are sender-controlled. The **underflow and the dead drop-branch are READ**; end-to-end delivery is **INFERRED** on those two conditions.
- **Guard presence:** the intended guard exists in form (`:172`'s error branch) but not in effect, because the helper it relies on does not implement the check for pool pbufs. `udphdr->len` (the UDP length field) is never consulted on the input path at all.

### 2.5 SMSTCPIP — checked clean / dissolved

- **DHCP and DNS parsing: not present to audit.** There is no `dhcp.c` or `dns.c` in `iop/SMSTCPIP/src/` and neither appears in the tree's `Makefile` object list (READ: file listing + `Makefile`). `LWIP_DHCP` is 1 only under `#ifdef PS2IP_DHCP` (`include/lwipopts.h:133-143`, otherwise 0), and `PS2IP_DHCP` is defined nowhere in the tree or its Makefile (grep, READ) — so the one DHCP-adjacent read, the unguarded UDP-destination-port peek at `ip.c:243-252` (which dereferences a `udp_hdr` at `iphdr + iphdrlen` with no `p->len ≥ iphdrlen + 8` check), is **compiled out of this build**. Dissolved for this pin/build; recorded so a future `-DPS2IP_DHCP` build re-opens it. DNS is served, if at all, outside this tree.
- **ARP (`etharp.c`): clean.** `etharp_arp_input` drops `p->tot_len < sizeof(struct etharp_hdr)` at `:424` before any field use (and the caller frees the pbuf on that path, `ps2ip.c:253`). The wire `hwlen`/`protolen` fields are never used as lengths anywhere in the file — parsing is fixed-layout over the checked 42-byte struct, and the reply path's copies use `netif->hwaddr_len` (6, set by SMSMAP `main.c:249`, not wire data). `etharp_ip_input` (`:391-400`) has no length check before reading the Ethernet/IP source fields, but those reads are fixed offsets ≤ 34 into the 1540-byte pool allocation (§0 containment) and feed only an ARP-cache insert — dissolved, not promoted.
- **Ethernet dispatch (`ps2ip.c:241-255`, live path — `QUEUE_INPUT` is 0 at `:40`):** reads the 2-byte EtherType with no `p->len ≥ 14` check. Fixed-offset, inside the pool allocation, no length is derived from it. Dissolved per §0.
- **ICMP (`icmp.c`): input clean, one over-read dissolved.** `icmp_input` checks `p->tot_len < 4` after the IP strip (`:65`) and `tot_len < sizeof(struct icmp_echo_hdr)` before the echo path (`:85`); the echo checksum walks the real pbuf lengths (`inet.s` `inet_chksum_pbuf`). `icmp_dest_unreach` (`:145`) copies a fixed `IP_HLEN + 8` = 28 bytes from `p->payload` even for a 20-byte IP-only packet that reached it via `ip_input`'s unknown-protocol branch — an 8-byte over-read that stays inside the 1540-byte pool allocation and lands in an outbound ICMP message. Dissolved per §0 (noted here so it isn't rediscovered as new).
- **IP header basics (`ip.c:201-230`):** `IPH_HL == 0` dissolves — `iphdrlen` 0 makes `inet_chksum(iphdr, 0)` return non-zero, so the packet dies at `:222`. `IPH_HL` 1–4 desynchronises the transport offset but every downstream layer uses the same `IPH_HL*4` consistently and all reads stay in-allocation — parser desync, not OOB; not promoted. `IPH_LEN < iphdrlen` is not an independent defect: its only continuations are the TCP/UDP/ICMP strips covered by TCPIP-3/TCPIP-4 and the ICMP check above (TCP's post-strip `tot_len` check at `tcp_in.c:121` and ICMP's at `icmp.c:65` do fire for the first strip).

## 3. SMSMAP — candidate

### SMAP-1 / Received-frame length from the buffer descriptor is never clamped to the pbuf pool size before the FIFO copy · READ (code chain), INFERRED (whether the EMAC can present a length > 1540)

- **Entry / provenance:** wire frame → SMAP hardware writes the RX buffer descriptor (BD) at `0xB0003200` → `iop/SMSMAP/smap.c:985-1050` (`SMap_HandleRXInt`).
- **Chain (READ):**
  1. `smap.c:1010`: `lLen = (lpRXBD->m_Len + 3) & ~3;` — `m_Len` is the hardware-filled `unsigned short` at `iop/SMSMAP/smap.h:39`. The only gate before use is the error-bit test at `:1012` (`!(lSts & SMAP_BD_RX_ERRMASK)`); **length itself is never compared to anything**.
  2. `smap.c:1014`: `pbuf_alloc(PBUF_RAW, lLen, PBUF_POOL)`. The pool branch of `pbuf_alloc` (`SMSTCPIP/src/pbuf.c`, PBUF_POOL case) assigns a **single** pool pbuf with `len = tot_len = length` — it neither chains nor rejects `length > PBUF_POOL_BUFSIZE` (1540).
  3. `smap.c:1018`: `SMAP_CopyFromFIFO(pBuf, lPtr)` — the assembly at `smap.c:819-884` loads its copy count from the pbuf's `tot_len` field (`lhu $s1, 8($a0)` at `:825`) and DMA/copies exactly that many bytes into `pBuf->payload`, whose backing store is one 1540-byte pool slot. A `tot_len` above 1540 therefore writes past the slot into the adjacent pool pbufs (pool slots are contiguous in `pbuf_pool_memory`, `pbuf.c` `pbuf_init`).
  4. `smap.c:1020`: the over-long pbuf is then handed to `ps2ip_input` as-is.
- **Guard presence:** none in software on this path — no `lLen > PBUF_POOL_BUFSIZE` (or `> SMAP` RX FIFO capacity) drop, in contrast to the TX path in the same file, which does check `lTXLen > m_TXFree` before copying (`smap.c:908`).
- **Reachability caveat (INFERRED):** whether a real SMAP EMAC will ever set `m_Len` above the standard 1518-byte frame (plus FCS/padding) without also setting an RX error bit is a hardware question this VM cannot settle; standard Ethernet framing suggests not, and no jumbo-frame enable was found in the tree (grep: no jumbo/oversize configuration; `main.c:250` sets `mtu = 1500`). The defect filed is the missing software clamp on a hardware/wire-supplied length at the exact point a copy is sized by it — if the hardware assumption ever fails (fault, clone hardware, future EMAC mode), the failure mode is a pool overwrite, not a dropped frame.
- **Checked clean in the same pass:** BD index advance is by fixed macro over the descriptor ring; error frames (`SMAP_BD_RX_ERRMASK`) are skipped and their FIFO space reclaimed at `:1024-1034` without copying; `SMap_Send` is internal-output only (lengths from the stack's own pbufs, TX-free check at `:908`, gather-copy into a statically-sized `sl_TXBuf[SMAP_TXMAXSIZE + tailpad]` at `:888` — chain lengths there are stack-generated, not external).

## 4. SMSUMS — candidates

### UMS-1 / LFN direntry sequence number is an unchecked index multiplier — writes up to ~800 bytes into a 128-byte name buffer, and −13 for sequence 0x40 · READ

- **Entry / provenance:** disc-supplied directory sector → `CacheRead` → `_get_direntry_start_cluster` (`iop/SMSUMS/src/ums_fat.c:580-582`, stack-local `fat_direntry lDir`) and `_next_direntry` (`:666-668`, same shape) → `_get_direntry` (`:411-461`).
- **Chain (READ):**
  1. An entry is classified as a long-name (LFN) entry solely by three disc bytes at `:420` (`m_RSHV == 0x0F && m_Res1 == 0x00 && m_Res2[0] == 0x00` — the standard LFN attribute pattern, fully attacker-controlled on a crafted disc).
  2. `:421`: `lOff = ((apLong->m_EntrySeq & 0x3F) − 1) * 13;` — `m_EntrySeq` is the entry's first disc byte. **No range check.** Legal LFN sequence numbers run 1–20; the field admits 0–63 after masking.
  3. `:423-440`: three loops copy up to 13 name characters to `apDir->m_Name[lOff++]`, i.e. at offsets `lOff … lOff+12`. The destination is `fat_direntry.m_Name[FAT_MAX_NAME]` = **128 bytes** (`:124`, `FAT_MAX_NAME` at `:21`).
  4. Concretely: sequence 11 already starts at offset 130 (past the buffer); sequence 20 (a *legal* value for a 247–255-char name) writes at 247–259; sequence 63 writes at **806–818**. The writes overrun `fat_direntry` into the rest of the caller's stack frame (`lDir` is a stack local in both callers, `:555` and `:638`). Sequence `0x40` (the "last entry" flag with ordinal 0) gives `(0 − 1) * 13` = **−13**: writes *before* the buffer. (Sequence 0 itself is accidentally pre-empted by the deleted/empty checks at `:417`, which test the same byte — `0x40` is not.)
  5. Termination doesn't save it: the NUL write at `:425`/`:441` happens at the same unchecked `lOff`, and `_set_dir` then does an unbounded `strcpy(apDir->m_Name, lpSrcName)` at `:513` into `fat_dir.m_Name[128]` (`:137`), with `_fat_dread` repeating the pattern at `:944` — so even a within-struct overrun leaves an unterminated 128-byte name for two further unbounded copies.
- **Guard presence:** none — no `EntrySeq` ordinal bound (e.g. `≤ 20` or `lOff + 13 ≤ FAT_MAX_NAME`) anywhere in `_get_direntry` or its callers.
- **Trigger:** opening or enumerating any directory on a USB stick whose directory cluster contains one crafted LFN entry. This is the tree's headline defect: a removable-media parser writing attacker-controlled offsets on the stack, reachable by the player's ordinary browse/open path.

### UMS-2 / READ CAPACITY sector size is stored verbatim — 0 divides by zero, >128 KiB overflows the cache buffer on the very first read · READ

- **Entry / provenance:** USB device-supplied SCSI READ CAPACITY (0x25) response → `UmsGetCapacity`, `iop/SMSUMS/src/ums_driver.c:300-321`.
- **Chain (READ):**
  1. `:312-313`: `m_MaxLBA = _int_be(&lBuf[0]); m_SectorSize = _int_be(&lBuf[4]);` — both device bytes, **no validation at all**: no zero check, no power-of-two/range check. (Contrast the same tree's BPB parser, which whitelists the *BPB's* sector-size field against {512, 1024, 2048, 4096} at `ums_fat.c:1048-1052` — the transport-level field that actually sizes buffers is the unvalidated one.)
  2. First uses, in `_ums_mount` order (`ums.c:200`: `UmsGetCapacity && FATFS_Init`, CacheInit only afterwards at `:202`): `FATFS_Init` calls `UmsRead(apDev, 0, apDev->m_pCacheBuf, lSecSize)` with `lSecSize = m_SectorSize` (`ums_fat.c:989, :996`). `m_pCacheBuf` is a fixed **131,072**-byte allocation (`ums.c:66`). `UmsRead` (`ums_driver.c:393-420`) computes `lnSectors = (aSize + m_SectorSize − 1) / m_SectorSize` — **division by the device value**: `m_SectorSize == 0` is a divide-by-zero before any transfer; a large claimed size (e.g. 262,144) with a correspondingly large claimed `m_MaxLBA` passes the `:398` clamp and `UsbmTransact` bulk-writes `aSize` device bytes into the 131,072-byte buffer.
  3. The same field divides again in `CacheInit` (`ums_cache.c:40`: `(32768 + m_SectorSize − 1) / m_SectorSize`) and sizes every `CacheRead` block read (fixed 32,768-byte transfers into the same cache buffer, `ums_cache.c` `CacheRead`), so even a surviving mount carries the bad geometry into all FAT parsing.
- **Guard presence:** none between the response and the stores at `:312-313`, and none at any use site.
- **Trigger:** a malicious or merely non-conformant USB mass-storage device (this driver is *also* the descriptor-parsing client — see USBD-1 note). A legitimate device returns 512/2048; the defect is that nothing enforces it.

### UMS-3 / `_set_dir_chain` treats a −1 chain error as a completed chain and reads `m_ClusterBuf[−1]` · READ

- **Location:** `iop/SMSUMS/src/ums_fat.c:482-501`.
- **Chain (READ):** the per-type chain walkers return **−1** when a FAT sector read fails (`_get_cluster_chain12/16/32`, e.g. `:270`, `:312`, `:343` — `CacheRead` NULL). `_set_dir_chain` at `:483-487` handles only the documented `0` = "buffer full, continue" case (`if (lChainSize == 0) {…} else lNextChain = 0;`), so −1 exits the loop as if the chain were complete; the `for` at `:488` runs zero times with `i == 0`; `:500` then unconditionally executes `apDir->m_LastCluster = lpFS->m_ClusterBuf[i − 1]` = `m_ClusterBuf[−1]` — a 4-byte read immediately before the 512-entry cluster array inside the heap-allocated `FATFS` (the preceding field, `m_PartRec`), whose value is latched as the file's last cluster and used by later seek/read positioning.
- **Contrast (READ):** the sibling caller `_get_direntry_sector_data` *does* handle it: `:401-403` — `if (lChainSize <= 0) return −1;`. The check exists in the file; this call site missed it.
- **Trigger:** a file whose FAT chain reaches a sector the device fails to return (corrupt FAT pointing outside the device, flaky media) during open. Impact as read: an in-struct-adjacent over-read and a garbage `m_LastCluster`, not a wild write — filed at that weight.

### UMS-4 / `_get_direntry_start_cluster` ignores `_get_direntry_sector_data`'s failure return and loops over uninitialised locals · READ (ignored return), INFERRED (loop extent)

- **Location:** `iop/SMSUMS/src/ums_fat.c:551-599`, call at `:566`.
- **Chain (READ):** `_get_direntry_sector_data` returns −1 on chain failure *without* writing `*apStartSec` or `*apDirSec` in that path (`:401-403`). The caller at `:566` discards the return value entirely and proceeds into `for (i = 0; i < lDirSec && lCont; ++i)` (`:568`) with `lDirSec` and `lStartSec` (`:557`) uninitialised stack values, calling `CacheRead(apDev, lStartSec + i)` at `:573`. A garbage non-positive `lDirSec` makes the call a spurious −ENOENT (the benign outcome); a garbage positive one makes it scan "directory entries" in whatever cached sectors the garbage start selects, feeding `_get_direntry` (see UMS-1) and the name comparisons at `:585-587` from unintended disc locations.
- **Guard presence:** none — this is the only one of the three `_get_direntry_sector_data` call sites that doesn't consume the result (`_next_direntry` at `:652` also discards it, but there `lDirSector`/`lStartSector` feed the identical pattern — same defect family; counted once, both sites named).
- **Impact label:** INFERRED — the extent depends on stack garbage; the defect (error return ignored, uninitialised use) is READ.

### 4.5 SMSUMS — checked clean / dissolved

- **BPB validation is genuinely present** (`FATFS_Init`, `ums_fat.c:1043-1062`): boot signature `0xAA55` required, zero-total-sectors rejected, BPB sector size whitelisted {512…4096}, cluster size whitelisted to powers of two 1–128. Fields *not* whitelisted (`m_nResSectors`, `m_nFATs`, `m_FATSize`, `m_RootSize`, partition `m_StartLBA`/`m_Size`) are used only as unsigned sector arithmetic feeding `UmsRead`/`CacheRead`, whose failure is NULL-checked at the chain call sites — a lying BPB gets wrong-sector reads and clean failures, not OOB memory access. Dissolved.
- **MBR partition scan** (`:1013-1023`) reads the four fixed 16-byte entries at offset 446 of a sector that was successfully read, and an unmatched scan falls back to start sector 0, which is then subjected to the BPB checks above. The MBR's own `0xAA55` is not checked *before* the scan — consequence bounded by the later BPB gate. Dissolved.
- **Cluster-chain walkers are cycle-safe** (`:249-355`): every iteration appends to the caller's buffer and the loops are bounded by `aBufSize` (512 / `DIR_CHAIN_SIZE`); a cyclic FAT chain terminates with the documented `0` return, it cannot loop forever or overrun `apBuf`. FAT entry values are used as sector indices through `CacheRead`, whose NULL return is checked at `:270/:276/:311/:342`. Clean.
- **`_data_clusters` unsigned underflow** (`:230-232`): reserved+FAT+root exceeding `m_nSectors` wraps to a huge cluster count and `_get_FAT_type` (`:357-372`) then picks FAT32 for a small disc — parser desync (wrong chain walker for the medium), but every subsequent access goes through the bounded walkers/`CacheRead` above. No memory consequence traced. Dissolved.
- **Short-name construction** (`:444-453`) is exactly bounded: ≤ 8 name chars + `'.'` + ≤ 3 ext chars + NUL at index ≤ 12 into `m_SName[13]`. Clean. (The long-name path is UMS-1.)
- **`_fat_read` (`:785-853`)** clamps `aSize` to the direntry's disc-supplied `m_Size` at `:808` and copies sector-by-sector with `lBufSize` re-clamped to `lSectorSize` at `:835-836` from `CacheRead` buffers; its chain handling reuses the bounded walkers. The disc-supplied `m_Size` also bounds `_fat_seek` at `:872`. No candidate in the read path itself (its inputs are poisoned by UMS-3/UMS-4 upstream, counted there).
- **Descriptor walking in `ums.c`** (`_ums_probe :40-56`, `_ums_connect :102-116`): `_ums_probe` checks `bNumInterfaces ≥ 1` and `wTotalLength ≥ sizeof(config) + sizeof(interface)` before touching the interface descriptor (`:42-44`) — a real guard. `_ums_connect` re-walks without repeating it and advances endpoint descriptors by the device-supplied `bLength` (`:113-115`) with no `bLength ≥ sizeof(UsbEndpointDescriptor)` or end-pointer check, stopping after `bNumEndpoints` steps; a zero `bLength` repeats the same descriptor rather than looping forever, and each step only feeds `UmsBulkProbeEndPoint`'s fixed-offset field reads. This is the client-side half of USBD-1 (the walk primitive and its contract live in USBD); counted there, not double-counted here.

## 5. USBD — candidate

### USBD-1 / Descriptor walk validates only `bLength ≥ 2` — a truncated descriptor is returned as a full struct and read at fixed offsets · READ

- **Entry / provenance:** device-supplied descriptor blob, fetched into a per-device static buffer by `fetchConfigDescriptors` (`iop/USBD/src/hub.c:378-414`) → walk primitive `doGetDeviceStaticDescriptor` (`iop/USBD/src/hcd.c:176-196`) → all client drivers.
- **Chain (READ):**
  1. `hcd.c:190-195`: the walk's only validations are `descBuf < dev->staticDeviceDescEndPtr` and `descBuf->bLength >= 2`. A descriptor whose `bLength` is, say, 2 or 4 but whose **type** matches the request is returned at `:191-192` as a complete `UsbConfigDescriptor*` / `UsbInterfaceDescriptor*` / `UsbEndpointDescriptor*`. The walk never checks `bLength ≥ sizeof(<requested struct>)`, nor `descBuf + bLength ≤ staticDeviceDescEndPtr` before the *next* advance, nor that at least the requested struct's bytes lie before `staticDeviceDescEndPtr` before returning it.
  2. Immediate consumers read fixed offsets beyond such a truncated descriptor: `hubDrvConnect` reads `confDesc->bNumInterfaces` (`hub.c:636`), `intfDesc->bNumEndpoints` (`:640`), `endpDesc->bEndpointAddress`/`bmAttributes` (`:647-651`); `fetchConfigDescriptors` itself reads `desc->wTotalLength` (offset 2, 4 bytes needed) at `hub.c:392/:397`; `openDeviceEndpoint` reads `wMaxPacketSizeHB/LB`, `bInterval`, `bEndpointAddress` (`hcd.c:75-76, :93, :123`). Those bytes are whatever follows in the static descriptor buffer — the tail of a previous descriptor, or, for a descriptor sitting at the end of the fetched region, bytes past `staticDeviceDescEndPtr` (still inside the 512-byte per-device allocation in most positions; past it only in the final position of the final device's buffer — stated, not exaggerated).
  3. Client drivers compound it by walking *past* USBD's primitive with no contract at all (SMSUMS `_ums_connect`, §4.5) — the primitive's `≥ 2` check is the only length discipline in the whole descriptor ecosystem.
- **Guard presence:** the *aggregate* size is guarded (see checked-clean below) — what is missing is the **per-descriptor** minimum-length check, which is the standard failure mode of USB descriptor parsers: aggregate bounds do not stop a 2-byte "endpoint descriptor" from being consumed as a 7-byte struct.
- **Impact label:** READ that the reads occur and are device-controlled in placement; INFERRED for any specific corruption — the concrete, provable consequence is connect/probe decisions and endpoint programming (`hcEd.maxPacketSize`, direction, type) made from bytes the device never sent as part of that descriptor.

### 5.1 USBD — checked clean / dissolved

- **Aggregate descriptor size is genuinely capped** (`hub.c:401-404`): before every config fetch, `staticDeviceDescEndPtr + readLen > staticDeviceDescPtr + usbConfig.maxStaticDescSize` (512, `usbd.c:36`) aborts with "Device descriptors too large" and the device is ignored. A `wTotalLength` of 65,535 therefore cannot overflow the static buffer — it gets the device dropped. This guard is why USBD has no analogue of SMAP-1.
- **The same advance-then-check order at `hub.c:390-393`** (advancing `staticDeviceDescEndPtr` by the previous config's `wTotalLength` before the `:401` check) dissolves on inspection: the advance only moves a pointer; the check runs before the next transfer is issued at `:407-409`, so no write ever lands past the cap.
- **Walk termination:** `bLength >= 2` at `hcd.c:190` means a zero/one-length descriptor stops the walk rather than spinning — the primitive cannot infinite-loop on device data. (Its insufficiency is USBD-1, a different claim.)
- **Hub descriptor handling is the file's own model of doing it right:** port count is rejected when `bNbrPorts > usbConfig.maxPortsPerHub` (8, `usbd.c:38`) before `hubSetupPorts` consumes it (`hub.c:592-597`, setup at `:569-587`), and `hubDrvConnect` clamps the hub-descriptor copy with `if (len > sizeof(UsbHubDescriptor)) len = sizeof(UsbHubDescriptor)` (`:671-675`). Both checked, both clean.
- **Endpoint programming clamps:** `openDeviceEndpoint` masks `hcMaxPktSize &= 0x7FF` (`hcd.c:117`) and clamps non-aligned control/out endpoints to `0x3E` (`:89-90, :113-114`). `bMaxPacketSize0` from the device descriptor is installed raw into the control endpoint at `hub.c:425` — a value of 0 or 255 misprograms OHCI packet size but no memory access is sized by it in the code read. Dissolved.
- **`requestDevDescrptCb` short-transfer path** (`hub.c:423-431`): a transfer returning fewer than 18 bytes re-requests the full descriptor rather than parsing the short one — only `bMaxPacketSize0` (byte 7) is consumed from the 8-byte peek, which the peek length covers. Clean as read.
- No string descriptors are fetched anywhere in the tree (grep: no `USB_DT_STRING` use), so the usual string-descriptor length surface does not exist here. `driver.c` / `interface.c` / `mem.c` contain no other device-data parsing (dispatch, endpoint bookkeeping, pool allocation with fixed sizes).

## 6. SMSDev9 and SMSPWROFF — disposition

- **SMSDev9 — limited parse, checked clean.** `card_find_manfid` (`ps2dev9.c:613-663`) walks PCMCIA CIS tuples in the card's attribute space — genuinely card-supplied data — and is, unusually for this codebase, guarded at every step: the walk is bounded by `spdend = 0x1000` (`:625-627`), the link byte is read only after a `spdaddr >= spdend` check (`:634-637`), the next-tuple target is rejected when `next >= spdend` (`:642-644`), and the MANFID tuple's 8 bytes are read only after `(spdaddr + 8) >= spdend` is excluded (`:647-653`). The EEPROM path (`read_eeprom_data`, `:357-370`, and `dev9GetEEPROM`, `:383-397`) moves a fixed 4×16 bits into a fixed `eeprom_data[5]` — no length exists to check. The remaining surface is internal: the ioctl switch has three fixed commands (`:863-873`), and `dev9RegisterIntrCb`'s unchecked table index is an argument from other IOP modules, not from any external source — inventoried, out of this round's external-parsing scope, not a candidate.
- **SMSPWROFF — no parse, inventoried.** Read in full (170 lines): a CDVD-interrupt hook testing two register bits, a SIF command send of a fixed 16-byte array, and a 4-slot callback table filled only by IOP-internal registrants. There is no buffer, length, or structure originating outside the console. No pass performed, by the decision rule in §1.
