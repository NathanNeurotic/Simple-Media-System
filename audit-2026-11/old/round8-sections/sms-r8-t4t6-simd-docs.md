### QPel filter constants vs the C table (check ii/iii)
- SPRAM filter block is `s_QPelConst` (`src/SMS_DSP.c:362–369`, 48 halfwords copied to `0x70000220` at `:373`): `0x220`=20, `0x230`=16, `0x240`=15, `0x250`=6, `0x260`=0xFF, `0x270`=1. The `0x240` (15) slot is loaded by **no** helper in either file region — it is not a missing load: no register in any lowpass body ever consumes a 15-coefficient (the 6-tap is built as 20·centre − 6·mid + 3·(6≫1) + 1·outer + 16 rounding, `psrah …,5`; see next bullet).
- Coefficient-register assignment is identical in every setter/helper: `$t6`=20 (`0x220`), `$t7`=16 (`0x230`, the ≫5 rounding addend), `$t8`=6 (`0x250`), `$t9`=`$t8≫1`=3, clamp `$t5`/`$s1`=0xFF (`0x260`), outer coefficient / avg-rounding `$s0`=1 (`0x270`). Setters: `_copy16` (114), `_copy8_16` (1499). In-span reloads at 916–919, 1505–1508, 1576–1578, 1650–1652, 1726–1728, 2016–2019 all draw from the same slots with the same roles; where a helper reloads only a subset (e.g. `_put_qpel8_16_h_lowpass` loads no `$t7`), the missing register is the one its `_copy*` prologue already set — verified per entry path.
- Multiply sequences are byte-identical between nominal siblings: the 16-op `pmulth/pmsubh/pmaddh` coefficient sequence of `_put_qpel16_h_lowpass` == `_avg_qpel16_h_lowpass` == both `_copy` variants; the 3-op sequence of the four 8_16 h-lowpass bodies is likewise identical. `mtsab/mtsah` shift-amount sequences are identical across all four 16-wide h bodies (`0,1,1,−1,3,4,6,1`) and across all four 8_16 h bodies (`0,1,−1,1,−1,1,−1`).
- Normalised diffs `_put_qpel16_v_lowpass` vs `_avg_qpel16_v_lowpass` and `_put_qpel8_16_v_lowpass` vs `_avg_qpel8_16_v_lowpass`: the **only** differences are the expected averaging insertions (load destination row, `paddh` dest, `paddh` rounding register, `psrlh …,1`) and scheduling. No coefficient, shift or offset diverges in any of the 16 (resp. 8) unrolled rows. Source-load offsets in all four v bodies form a pure +16 progression (17 loads 0…256 for 16-wide; 9 loads 0…128 for 8_16) — script-verified, zero deviants.
- Rounding-register provenance for the vertical avg passes (the registers the helpers consume but do not set): `DSP_AvgQPel16MC02` sets `$s0` in the call delay slot via `psrlh $s0,$t5,7` — `$t5` is the 0xFF-per-halfword clamp from `_copy16`, 255≫7 = 1 per halfword, i.e. the (a+b+1)≫1 rounding constant; `DSP_AvgQPel816MC02` builds `$s3`=1 via `pnor`+`psrlh …,15`; `DSP_AvgQPel816MC12` copies `$s3` from `$t9` **before** re-deriving `$t9`=3, at a point where `$t9` still holds the 1s left by `_put_qpel8_16`. All three are correct, if subtle. (Wrapper bodies are outside the assigned span; used only as cross-check (i).)
- Shifts census (span): QPel — `psrah 5` ×38, `psrlh 1` ×58, `psrlh 15` ×3 (the 1s-generators), `psrlh 8` ×2 (0xFF clamp construction in h bodies), `sll 4` ×6 (row-stride ×16), `srl 16` ×1. No other shift amount exists in the span. The `384($v0)` second-block loads in every h body equal `sizeof(SMS_MacroBlock)` = 256+64+64 (`include/SMS.h:198–204`) — same constant Round 7 verified for `SMS_DSP_MMI.S`.

### QPel near-misses cleared
- `_put_qpel8_16` tail row (`:1565` region) and `_put_no_rnd_qpel8_16` tail use `ppacb $t0,$t2,$t0` where the loop bodies use `ppacb $t0,$zero,$t0`, and `$t2` there is stale. Harmless by construction: the tail store is `sd` (8 bytes), which keeps only the low half of the packed register — the half packed from the **second** operand (`$t0`, the fresh averaged row). The stale-`$t2` half is discarded. The 16-wide tails set their pack source fresh and are exact.
- One row of `_avg_qpel16_v_lowpass` packs with `ppacb $t0,$t0,$t0` where its put sibling uses `ppacb $t0,$zero,$t0` — same `sd`-discard argument; the stored 8 bytes are identical.
- `_copy16` vs `_copy8_16`: loop counts 17 vs 9 and return adjustments −256 vs −128 scale exactly with the 16- vs 8-row scratchpad copies they perform.

### libmpeg constants (checks i/ii/iii)
- Clamp constant in all three `_MPEG_add_block_*` and the `_MPEG_put_block_il` tail: `pnor` + `psrlh …,8` = 0xFF per halfword, both lanes, every iteration. `_MPEG_put_block_fr/fl/il` source-offset sets are identical where the modes share phases (fl and il: `0,16,32,48` then `256…368`; fr is the frame-only subset).
- Block geometry is uniform across all 16 `_MPEG_{put,avg}_{luma,chroma}{,_X,_Y,_XY}` functions: luma second-block offset **384**, block advance **512**; chroma offsets **0/64/384/448**, advance **704**, destination second-plane offset **128**. No function deviates in any lane or iteration (scripted offset census: the full span's offset multiset contains no singleton that breaks a progression or a sibling pattern).
- Rounding is width-correct per direction in both files' terms: X and Y passes add **1** then `psrlh …,1` (`pnor`+`psrlh 15` = 1s); XY passes add **2** then `psrlh …,2` (1s `psllh 1` = 2) — identical in luma and chroma, put and avg variants (`_MPEG_put_luma_XY:1741–1746` vs `_MPEG_put_chroma_XY:1770–1813` vs both avg XY bodies). The non-directional avg bodies use the `pcgth/pceqh` + `psrlh 15` + `por` construction that adds 1 iff the halfword sum is ≥ 0 — sums of two byte-origin halfwords are never negative, so this is exactly (a+b+1)≫1 — in both lanes of all four avg families, including the second-stage average in the X/Y/XY avg bodies.
- `_MPEG_add_block_*` totals: frfr 6 iterations × 64 B = 384 B (one full MB: 256 Y + 64 Cb + 64 Cr, matching `SMS_MacroBlock`); ilfl/frfl 4 luma iterations (2 fields × 32 B) + 2 chroma iterations = the same 256 + 128. The frfl chroma phase's interleaved load order (256, 320, 272, 336 → +32) is the field-weave order and is identical in both its halves.
- `_MPEG_do_mc` (1442): luma shifts `sll 4` (×16) vs chroma `sll 3` (×8) match the 16-wide/8-wide geometry; the `+256`/`+768` chroma adjustments and field offsets 0…36 are internal to the libmpeg calling convention (no C struct defines them independently — same disposition as Round 7, not re-filed).
- `_MPEG_dma_ref_image` (1397): entry stride multiplier built as 4+380 = **384**, `$a0` advance **1536** = 4×384, DMAPack entry 32 B with count clamped to 4 = the 128 B `s_DMAPack` (Round 7 verified the buffer; the arithmetic here is consistent with it). Negative offsets (−11264/−11232/−11136/−11216/−16) are the DMA/IOP hardware-register window under `lui 0x1001`, uniform in form.
- `_MPEG_Set16` (2300): patch bytes 0x80/0x40/0x70/0x7C are the deliberate self-modifying-code opcode bytes already dispositioned in Round 7 (SMS-156/157 territory — not re-filed).

### Singleton-deviation scan
A scripted scan grouped every repeated instruction template per function and flagged any immediate held by exactly one instance of a template repeated ≥ 4 times. All flags raised were (a) the designed `mtsah` shift progression, and (b) arithmetic-progression row offsets (0,16,32,…). **No constant-position deviant exists in either span.**
