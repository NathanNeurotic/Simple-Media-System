### SMS-158 — SMSTCPIP `do_connect` ignores `tcp_connect`'s return: a synchronous failure hangs `netconn_connect` forever / Category 6
- **Locations:** `iop/SMSTCPIP/src/api_msg.c:515-521`; failure source `iop/SMSTCPIP/src/tcp.c:488-530`, `iop/SMSTCPIP/src/tcp_out.c:296-308`; blocked waiter `iop/SMSTCPIP/src/api_lib.c:286-315` (`sys_mbox_fetch` at :312).
- **Problem:** The TCP branch of `do_connect` relies entirely on the `do_connected` callback to post the completion mbox. If `tcp_connect` fails *synchronously* — `tcp_enqueue` returns `ERR_MEM` when the shared `MEMP_NUM_TCP_SEG` (40) or pbuf pools are exhausted — the callback is never invoked, `err_tcp` never fires (no connection was ever established), and nothing ever posts to `conn->mbox`. The calling thread (e.g. the SMB module in `netconn_connect`) blocks in `sys_mbox_fetch` permanently: a wedged module, not an error return. Every sibling handler either posts unconditionally (the UDP branch of the same function, :510-512) or checks its result (`do_write` checks `tcp_write`, :664-673; `do_listen` checks `tcp_listen`, :567-575). Parent-verified: the `tcp_connect(...)` call at api_msg.c:~518 discards its return value.
- **Fix:** Capture `tcp_connect`'s return in `do_connect`; on error, store it in `conn->err` and post the completion mbox directly, exactly as the early-allocation-failure exits of the same function already do (:462-466).
- **Benefit:** Connection attempts under memory pressure fail with `ERR_MEM` instead of deadlocking the connecting module.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ code; INFERRED only on which exhaustion interleaving a given workload hits first).

### SMS-160 — AAC two-step Huffman size arrays disagree with the actual second-stage table counts in both directions — 5 of 7 non-trivial entries are wrong, so the bound the decoders check against is not the bound that exists / Category 6
- **Locations:** size arrays `src/SMS_AAC.c:2307-2309` (`hcb_2_quad_table_size`), `:2355-2357` (`hcb_bin_table_size`), `:2746-2748` (`hcb_2_pair_table_size`); second-stage tables `:2197-2227` (`hcb1_2`), `:2229-2252` (`hcb2_2`), `:2254-2301` (`hcb4_2`), `:2530-2563` (`hcb6_2`), `:2565-2587` (`hcb8_2`), `:2589-2643` (`hcb10_2`), `:2645-2740` (`hcb11_2`); consumers `src/SMS_AAC.c:6467`, `:6481`, `:6513`, `:6534`.
- **Problem:** Counts verified by two independent script methods (both agree). Declared vs actual: quad codebooks 1/2/4 declare 114/86/185 vs actual 113/85/184 (+1 each); pair codebooks 6/10 declare 126/210 vs actual 125/209 (+1 each); pair 8 exact (83); pair 11 declares 373 vs actual 374 (−1); the binary family (161/161/127/337) is exact. The tables themselves are internally consistent — script-verified: for every codebook, `max(first_stage.offset + 2^extra_bits − 1)` equals exactly the last valid second-stage index — so the second-stage tables are the right length and the size arrays are hand-maintained constants that have drifted, in both directions. Parent-verified: the declared arrays read `{0, 114, 86, 0, 185, …}` and `{…, 126, …, 83, …, 210, 373}` at :2307-2309/:2746-2748. Consequence, stated precisely: today the practical exposure is bounded, because the checks at :6467/:6534 run *after* the table has already been indexed (that placement defect is SMS-123, already filed — not repeated). The new defect is that the bound values themselves are wrong: any fix that moves the SMS-123 check before the read would still admit offsets 1–2 entries past the end for codebooks 1, 2, 4, 6, 10, and the −1 for codebook 11 sits exactly at its maximum reachable offset (373), so tightening the comparison to `>=` during such a fix would falsely reject valid codebook-11 streams. A bounds fix built on these arrays is a bounds fix that doesn't bound.
- **Fix:** Replace the hand-written size constants with values derived from the tables themselves (entry-count expressions / `sizeof` division at the pointer-table definition site), or correct the five wrong entries (114→113, 86→85, 185→184, 126→125, 210→209, 373→374) and add a host-side assertion that each size equals its table's entry count.
- **Benefit:** The only bounds the two-step decoders have become true bounds; unblocks a correct SMS-123 remediation instead of one that preserves a 1–2 entry over-read.
- **Effort:** S · **Risk:** Low · **Confidence:** READ — all counts double-verified by script, first-stage reachability computed from the tables themselves, consumers line-read. No upstream comparison needed: the inconsistency is internal to this file.

### SMS-161 — DTS scale-factor quantizer tables end in zeros: `scale_factor_quant6[63] = 0` and `scale_factor_quant7[125..127] = 0` break a strictly increasing 63/125-entry run — the largest scale factors decode as silence / Category 6
- **Locations:** `src/SMS_DTS.c:1108-1125` (`scale_factor_quant6[64]`), `src/SMS_DTS.c:1127-1160` (`scale_factor_quant7[128]`); consumers `src/SMS_DTS.c:11369-11370` (table select), `:11383`/`:11397` (`scale_table[scale_sum]`), `:11440` (LFE).
- **Problem:** Script-verified structure (READ): `scale_factor_quant6` is strictly increasing over indices 0–62 (1 … 8,317,638 = 0x7EEAC6) and then index 63 is `0`. `scale_factor_quant7` is strictly increasing over indices 0–124 (same maximum) and then indices 125–127 are `0, 0, 0`. Parent-verified: both tables' literal tails read `…, 0x007EEAC6, 0x00000000` and `…, 0x007EEAC6, 0x00000000, 0x00000000, 0x00000000`. The zero indices are directly reachable from the bitstream, not just via the cumulative-sum path already covered by SMS-138: mode 5 does `scale_sum = bitstream_get(state, 6)` (:11380, parent-verified) → index 63 is a legal 6-bit value; mode 6 does `bitstream_get(state, 7)` (:11382) → indices 125–127 are legal 7-bit values; the LFE path reads `scale_factor_quant7[bitstream_get(state, 8)]` at :11440 → indices 125–127 give `lfe_scale = 0` (the 128–255 overrun is SMS-139, already filed — this finding is the separate in-bounds wrong-value defect). Effect: a subband (or the LFE channel) whose scale factor should be the *largest* in the table is instead multiplied by 0 — silent subband/LFE on otherwise valid streams that use the top scale-factor codes. Distinct from SMS-138 (cumulative sum as unchecked index — a bounds defect) and SMS-139 (8-bit LFE index — a bounds defect): here the indices are in-bounds and the *stored values* are wrong.
- **Fix:** Restore the missing tail values of both tables from the DTS reference tables; do not invent values locally — the correct continuation must come from the spec/upstream table. As a guard, the strictly-increasing property of both tables can be asserted by a host-side table test.
- **Benefit:** Correct decoding of the loudest scale-factor steps instead of silent subbands/LFE; removes a wrong constant that no bounds fix (SMS-138/139) would catch.
- **Effort:** S (four values, once the reference values are in hand) · **Risk:** Low — changes only entries that currently produce 0 (silence); no valid decode today depends on them being 0 · **Confidence:** READ for the zero tails, the strictly-increasing structure, and the direct bitstream reachability; INFERRED for the correct replacement values — upstream/spec comparison is explicitly required; no in-repo copy of either table exists to diff against (whole-tree duplicate scan found no second copy).

### SMS-164 — SMSTCPIP `do_bind` is the only API handler that does not NULL-check its PCB allocation / Category 6

- **Effort:** S · **Risk:** Low · **Confidence:** High (READ for the missing check and the dereference chain; INFERRED for the re-bind-after-error reachability).

### SMS-165 — USBD done-queue isochronous cleanup clears the wrong LUT slot, leaving stale IoRequest pointers / Category 6

### SMS-167 — SMSTCPIP `netbuf_ref` dereferences a possibly-NULL `pbuf_alloc` result (UDP send under pbuf exhaustion crashes) / Category 6
- **Locations:** `iop/SMSTCPIP/src/api_lib.c:70-80`, sink `:76`; NULL return proven at `iop/SMSTCPIP/src/pbuf.c:202-207` (pool is `MEMP_NUM_PBUF` 40); caller `iop/SMSTCPIP/src/sockets.c:413` (`lwip_send` UDP path, also unchecked).
- **Problem:** `netbuf_ref` assigns `buf->p = pbuf_alloc(PBUF_TRANSPORT, 0, PBUF_REF)` and immediately writes through `buf->p` three times. - **Effort:** S · **Risk:** Low · **Confidence:** High (READ).

### SMS-168 — SMSMAP PHY reset result is discarded and the LINK flag is never cleared: a dead PHY leaves SMAP reporting link-up / Category 6
- **Locations:** declaration `iop/SMSMAP/smap.c:311` (`int _smap_phy_reset(void)`); discarding caller `iop/SMSMAP/smap.c:692-697` (`SMap_Reset` is `void`); flag set only on the asm success path (`smap.c` asm :510-513) and by `SMap_Start` (bit 0 only); consumer `iop/SMSMAP/smap.c:904` (`SMap_Send` returns `SMap_Con` only when `SMAP_F_LINK` is clear).
- **Problem:** `_smap_phy_reset` computes a real result (link = 1; timeout/no-link exits return −1/0 — the BMCR-reset poll gives up after 9 retries in the asm) and its success path ORs `SMAP_F_LINK` into `g_SMAP.m_Flags`. - **Fix:** Have `SMap_Reset` clear `SMAP_F_LINK` before the PHY reset and set it only from `_smap_phy_reset`'s returned link result (or return/propagate the result to the two `SMap_Reset` callers).
- **Benefit:** Link state again tracks the PHY; senders get `SMap_Con` on a dead link instead of silent black-holing with a success return.
- **Effort:** S · **Risk:** Low · **Confidence:** INFERRED (C side READ — the `int` return, its discarding, and the :904 consumer; the set-without-clear claim rests on reading the asm flag stores).

### SMS-169 — SMSMAP `_start` returns resident-end unconditionally over unchecked kernel-object creation / Category 6
- **Locations:** `iop/SMSMAP/main.c:336-343` (`CreateEventFlag` :338, `CreateMutex` :339, `CreateThread`+`StartThread` :341, `return MODULE_RESIDENT_END` :343).

- **Effort:** S · **Risk:** Low · **Confidence:** High (READ code; INFERRED for kernel-call failure modes).

### SMS-171 — SMSMAP transmit: chained-pbuf gather copies `tot_len` bytes into a 1,520-byte static buffer bounded only by the 4,096-byte FIFO credit / Category 6
- **Locations:** `iop/SMSMAP/smap.c:886-921` — buffer `:888` (`sl_TXBuf` = 380 words = 1,520 bytes; `SMAP_TXMAXSIZE` 1514 at :17), the only length gate `:908` (`lTXLen > lpSMap->m_TXFree`, where `m_TXFree` is 4096, `smap.c:708`), gather loop `:914-919` (no per-copy or cumulative bound against `sl_TXBuf`).
- **Problem:** For a chained pbuf, `SMap_Send` linearises the chain into `sl_TXBuf` with `mips_memcpy` per link. The gate that runs first compares the rounded length against the TX *FIFO credit* (4,096), not against the gather buffer's capacity (1,520). Any chain with `tot_len` in (1520, 4096] passes the gate and the gather writes past the static buffer into adjacent `.bss`. No in-tree producer was found that emits >1,514-byte link frames (the netif MTU is 1500, `main.c:250`), so this is latent rather than live — but the function itself enforces the wrong bound, and it is the stack's only TX entry point.
- **Fix:** Reject `lPackLen > SMAP_TXMAXSIZE` in `SMap_Send` (return `SMap_TX`) before the gather, so the checked bound is the buffer actually being written.
- **Benefit:** The TX path's safety no longer depends on every present and future caller respecting the MTU; one comparison closes a static-buffer overwrite.
- **Effort:** S · **Risk:** Low · **Confidence:** High (READ for the bound mismatch; INFERRED — no in-tree producer of an oversize frame found).

### SMS-173 — AC3 IMDCT entry points take a bias parameter that is never used; the caller's per-channel bias computation is silently dropped / Category 1
- **Locations:** `src/SMS_AC3_imdct.c:533` and `:579` (signatures; `aBias` occurs nowhere else in either body — parent-verified: a full-text search of the file returns only the two signature lines); callers `src/SMS_AC3.c:2401, :2426-2434, :2475-2480`; bias plumbing `src/SMS_AC3.c:546, :586, :2593` and `include/SMS_AC3.h:94` (`m_Bias`).
- **Problem:** Both IMDCT entry points accept `sample_t aBias` and ignore it. The caller side maintains the fiction that it matters: `_ac3_frame` stores the literal `384` into `s_AC3Ctx.m_Bias`, and `_ac3_block` computes a per-channel `lBias` (from `_ac3_downmix_coeff`'s channel mask) solely to pass it into these two functions — for channels that actually have coefficients the value goes nowhere. The one place the bias value has any effect is the *no-coefficient* fill at `src/SMS_AC3.c:2440`, which writes `lBias` directly and does not involve the IMDCT at all — and even there the value is arithmetically inert: the float-to-int converters only shift right 15 and clamp, so a raw bias of 384 contributes `384 >> 15 = 0` to every converted sample (384 is the float-era liba52 magic number carried into a fixed-point port as a raw integer). - **Fix:** Delete the third parameter from both functions and from the two extern declarations at `src/SMS_AC3.c:174-175`, and drop the argument at the five call sites. Whether to also remove the now-fully-dead `m_Bias`/`lChanBias` plumbing in `SMS_AC3.c` is a second, separate deletion; the `:2440` fill is the one site whose stored bytes would change (converted output is identical either way, per the shift arithmetic).
- **Benefit:** Removes a misleading contract: today a reader (or a future port) reasonably believes per-channel bias is applied inside the transform and will debug audio levels in the wrong place. Net deletion, no new code.
- **Effort:** S · **Risk:** Low (parameter removal is mechanical; output samples provably unchanged because the value is never read) · **Confidence:** High (READ).

### SMS-177 — AC3 IMDCT: dead instructions in `_ifft2` (and one in `BUTTERFLY_ZERO`) are overwritten before any read / Category 1
- **Locations:** `src/SMS_AC3_imdct.c:290-295` (`_ifft2` inline asm), second site `:376` (`BUTTERFLY_ZERO`).
- **Problem:** Straight-line register dataflow, readable directly from the listing. In `_ifft2`: `ld T0, 0(apBuf)` (:290) feeds only `pcpyld T0, T0, T0` (:292), whose result is overwritten by `ld T0, 16(apBuf)` (:293) before any instruction reads `T0`; identically `ld T1, 8(apBuf)` (:291) → `pcpyld T1, T1, T1` (:294) → overwritten by `ld T1, 24(apBuf)` (:295). Four instructions — two of them scratchpad loads — execute on every `_ifft2` call (once per `_ifft8`, hence pervasively in both IMDCTs) and affect nothing. A consequence of the same dataflow, stated at its exact weight: as written, every store in `_ifft2` derives solely from the loads at offsets 16/24, so the block's first 16 bytes contribute to no output — whether the intended 2-point stage needed those inputs cannot be settled from this file, and this finding does **not** assert a transform bug; it asserts only that the four instructions are dead as written. Second site: `BUTTERFLY_ZERO`'s `pxor $at, $at, $at` (:376) is immediately overwritten by `nor $at, $zero, $zero` (:377), which does not read `$at`.
- **Fix:** Delete the four dead instructions in `_ifft2` and the dead `pxor` at :376. Do not "repair" the stage by inventing the missing term — if the maintainer believes the stage itself is wrong, that is a separate hardware A/B question against a reference IMDCT, not a cleanup.
- **Benefit:** Five dead instructions removed from the hottest inner loop of AC3 decode; the `_ifft2` listing afterwards shows exactly the dataflow it actually implements.
- **Effort:** S · **Risk:** Low for the deletion itself (dead by dataflow — register state after the block is unchanged); the surrounding stage's correctness is explicitly out of claim · **Confidence:** High on deadness (READ — complete instruction trace of both blocks).

### SMS-178 — AC3 IMDCT: `_ifft128` open-codes `_ifft64`'s entire body instead of calling it / Category 2

- **Effort:** S · **Risk:** Low (statement-for-statement identical) · **Confidence:** High (READ — both bodies read side by side).
