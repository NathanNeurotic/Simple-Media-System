### SMS-158 — `do_connect` ignores `tcp_connect`'s return — VERIFIED

- **Locations claimed vs actual:** `api_msg.c:515-521` — exact: TCP case at :515, `setup_tcp` at :517, `tcp_connect(…, do_connected)` at :518-519 with the return discarded, no post in the branch. Blocked waiter `api_lib.c:286-315` — exact: `netconn_connect`, `sys_mbox_fetch(conn->mbox, &mem)` at :312.
- **Sibling census (re-checked, not sampled):** the UDP branch of the same function posts unconditionally (`api_msg.c:510-511`); `do_write` captures `err = tcp_write(…)` at :664, stores it in `conn->err` at :673 and posts unconditionally at :685; `do_listen` captures `tcp_listen`'s result and NULL-checks it at :567-575; the early allocation-failure exits of `do_connect` itself set `conn->err = ERR_MEM` and post at :462-466, :472-476, :482-486, :493-497. The TCP connect branch is the only completion path in the function that neither posts nor checks.
- **Permanence of the hang (strengthened beyond the original):** on `tcp_enqueue` failure the PCB has already been put in `SYN_SENT` and registered (`tcp.c:516-520`) but no segment was enqueued, so `unacked == NULL` and `nrtx == 0`. In `tcp_slowtmr` (`tcp.c:539-575`) retransmission requires `unacked != NULL` (:563) and removal requires `nrtx == TCP_SYNMAXRTX` or `TCP_MAXRTX` (:557-560); `nrtx` is only advanced by retransmission, so neither ever fires. `poll_tcp` (`api_msg.c:146-157`) only signals `conn->sem` in WRITE/CLOSE states and never posts `conn->mbox`. `err_tcp` (:177-205) is therefore never invoked for this PCB. The hang is permanent, not a timeout-delayed error. A second synchronous return exists — `ERR_VAL` when `ipaddr == NULL` (`tcp.c:500`) — which fails the same way; it does not weaken the finding.
- **Verdict:** VERIFIED in full, mechanism and consequence.

- **Internal-consistency claim re-derived:** for all seven two-step codebooks, first-stage max-reachable equals exactly the last valid second-stage index (table above, columns 5 = 6). The second-stage tables are right-sized; only the bound arrays drifted.
- **Consequence arithmetic:** the existing check is `if (offset > size) return 10`. - **Interlock with SMS-123 (explicitly requested):** SMS-123's core defect stands — the use at `SMS_AAC.c:6464`/`:6531` (`.bits` read for `SMS_SKIP_BITS`) precedes the check at :6467/:6534. But SMS-123's withdrawn sub-claim — "a script count shows the declared sizes are maximum valid indices" — is **refuted by this recount**: the declared values are maximum valid indices for no codebook except 11 (for 1/2/4/6/10 they are max+2; they are not entry counts either, except by coincidence for none — counts are max+1). Therefore a fix that only reorders SMS-123's existing check before the use still admits the 1–2-entry over-read for codebooks 1, 2, 4, 6, 10; and a fix that "corrects" the comparison to `>=` while treating the declared arrays as counts would falsely reject codebook 11's valid maximum offset 373. Correct remediation order: first make the bound values true (declared := actual−1 if the `>` form is kept, or := actual with `>=`), then move the check before the first use. SMS-160's numbers being right is what makes this ordering necessary; had they been wrong, SMS-123's reorder alone would have sufficed.
- **Verdict:** VERIFIED in full, including the fix-ordering consequence.
