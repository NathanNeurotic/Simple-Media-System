## Full reasoning

### SMS-129 — lwIP TCP data-offset never validated — **VERIFIED**
- Claimed vs actual: `tcp_in.c:157-158` exact (`hdrlen = TCPH_HDRLEN(tcphdr); pbuf_header(p, -(hdrlen * 4));`, return ignored); root helper `pbuf.c:291-317` exact.
- Mechanism re-derived: `pbuf_header` POOL/RAM branch (`pbuf.c:295-302`) only rejects a payload move that lands before `p + sizeof(struct pbuf)` — a *forward* move (negative `header_size`) can never trip it, and there is no comparison against `p->len`. `p->len += header_size; p->tot_len += header_size` (`:312-313`) are u16 additions and wrap. The REF/ROM branch (`:304-308`) does test length, exactly as claimed. `TCPH_HDRLEN` (`tcp.h:176`) yields the wire nibble 0–15, unchecked against 5 or against `p->tot_len`. The only earlier length test is `tcp_in.c:121` (`p->tot_len < sizeof(struct tcp_hdr)` after the honoured IP strip), and the TCP checksum (`:138-152`) is computed over the true length *before* the bad move at `:157`, so a correctly checksummed 20-byte segment with data-offset 15 passes and wraps.
- `inseg.len = p->tot_len` at `:284` exact; `tcp_parseopt` (`:1161-1201`) re-derives the same claimed hdrlen and walks `opts[c]`, `opts[c+1]`… bounded only by it — consequence surface as filed.
- Correction to the illustrative arithmetic only: with the `:121` guard's minimum `tot_len` of 20 and max `hdrlen*4` of 60, the wrapped value is 65,476, not ≈65,492 (65,492 would require `tot_len` 16, which `:121` drops). Magnitude and mechanism unchanged.
- Guard hunt: no `hdrlen` validation anywhere in `tcp_input` before `:158`; `ip_input` (`ip.c:217`, `:230`) checks only the IP header length and shrinks via `pbuf_realloc` (shrink-only, `pbuf.c:248`). Nothing defeats the finding.

### SMS-130 — lwIP UDP short datagram — **VERIFIED**
- Claimed vs actual: `udp.c:172` exact (single strip of `UDP_HLEN + IPH_HL*4` with the drop branch hanging off `pbuf_header`'s return); restore/strip at `:309`/`:341` exact; delivery `pcb->recv` at `:344` (claimed :342-344). Root helper as SMS-129. `udphdr->len` is indeed never consulted on the input path.
- Mechanism re-derived: an IP payload of `u < 8` bytes gives `p->tot_len = 20 + u` on entry; the strip subtracts 28, wrapping `len`/`tot_len` to 65528 + u (the finding's figure is exact) and returning 0 for pool pbufs (SMS-129 root), so the "drop short packets" branch is dead for exactly its named case. Ports are read from `udphdr = payload − 8` after the strip, i.e. the first 4 IP-payload bytes — attacker-controlled for `u ≥ 4`, and for `u < 4` the remaining bytes are frame bytes beyond the IP total length that remain in the pool buffer because `pbuf_realloc` only adjusts lengths (`ip.c:230`, `pbuf.c:242-271`).
- Checksum gate re-derived (the subtle part, and it works in the attacker's favour): `:309` restores 8 bytes, wrapping `tot_len` back to exactly `u`; `inet_chksum_pseudo(..., p->tot_len)` at `:330` therefore checksums only the truncated window, and the gate at `:327` is skipped entirely if the checksum field (bytes 6–7 of the purported UDP header, reachable via frame padding) is 0. `:341` re-strips, restoring the wrapped ≈65,528 + u length for `pcb->recv`.
- Delivery extent: `sockets.c:346-353` takes `buflen = netbuf_len(buf)` (the wrapped `tot_len`) and copies `min(user_len, buflen)` via `netbuf_copy_partial` (`api_lib.c:82-119`), which copies by per-pbuf `p->len` — also wrapped — so an application requesting more than the ~1,540 B remaining in the pool slot is handed bytes past it. Bound-PCB + checksum conditions are satisfiable as shown. Nothing upstream (IP layer, etharp) validates the UDP length.

### SMS-133 — Vorbis `oggpack_read`/`oggpack_look` near-end over-read — **WEAKENED**
- Claimed vs actual: both functions at the claimed lines (`SMS_OGG.c:2939-2974`, `:4302-4329`), guard text quoted accurately (`:2946-2949`, `:4309-4311`).
- Refutation of the main mechanism, by algebra: let `E = endbyte`, `S = storage`, `A = anBits` *after* `A += endbit` (`:2944`). Fall-through requires `E + 4 >= S` **and** `E*8 + A <= S*8`. The reads touch `ptr[i]` for `i = 1` iff `A > 8`, `i = 2` iff `A > 16`, `i = 3` iff `A > 24`, `i = 4` iff `A > 32 && endbit`. For any `i >= 1`, `A > 8i` gives `A >= 8i + 1`, and the fall-through condition gives `A <= (S − E)*8`, hence `8i + 1 <= 8(S − E)`, i.e. `i <= S − E − 1`, i.e. `E + i <= S − 1` — **in bounds**. When the guard is not entered (`E + 4 < S`), `ptr[4]` is the highest possible read and `E + 4 <= S − 1` — in bounds. Once `E > S`, the total-bits test always fires and no read happens. So the claimed "within the last 4 bytes, few bits requested → reads of `ptr[1..3]` (and `ptr[4]`) past the packet buffer" cannot occur: the second condition the finding quotes is precisely the bound that prevents it.
- Surviving residue (the exact narrower condition): `ptr[0]` is read unconditionally. With `A == 0` (a 0-bit request with `endbit == 0`) at `E == S` exactly, the total-bits test is `S*8 + 0 > S*8` = false, execution falls through, and `ptr[0]` reads **one byte** one past the packet (the value is then masked to 0 by `mask[0]`). Reachability is code-level only: a 0-width field (e.g. `modebits == 0` when `modes == 1`, `SMS_OGG.c:3972` + `:4171`; `ilog(...)`-derived widths elsewhere) requested at the exact moment the packet is fully consumed. No ≥1-bit or multi-byte over-read survives.
