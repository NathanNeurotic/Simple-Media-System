## RE-SMS-025 — WEAKENED
- Evidence I read: `iop/SMSTCPIP/include/lwip/ip.h:75-82` (`IP_PCB` = `local_ip, remote_ip, so_options(u16), tos(u8), ttl(u8)`), included identically at the head of both `struct tcp_pcb` (`include/lwip/tcp.h:205`) and `struct udp_pcb` (`include/lwip/udp.h:56`); `iop/SMSTCPIP/src/sockets.c:1004,1037-1063,1197-1247` (actual processing in `lwip_getsockopt`/`lwip_setsockopt` at `sockets.c:878ff/1077ff`); IPPROTO_TCP early return `sockets.c:955` (get) and the matching setsockopt validation switch; `iop/SMSTCPIP/src/api_lib.c:121-166`; `iop/SMSTCPIP/src/api_msg.c:183,277-330`.
- Reasoning (defeating/narrowing evidence): (1) The headline cross-struct corruption claim is **false** for the fields actually accessed at SOL_SOCKET/IPPROTO_IP level: `so_options`/`tos`/`ttl` live in the common `IP_PCB` prefix at identical offsets in both PCBs, so accessing them via the `pcb.tcp` union member on a UDP socket reads/writes the correct field — this is lwIP's intended idiom, not corruption. (2) The TCP-only fields (`flags`/`keepalive`) are unreachable for UDP: both functions `return 0` in the validation phase when `conn->type != NETCONN_TCP` before any processing. (3) "PCB never created (socket() then setsockopt before bind/connect)" is **false**: `netconn_new_with_proto_and_callback` runs `do_newconn`, which allocates the PCB at socket creation; on failure it frees the conn and returns NULL, so no socket exists. `do_bind`/`do_connect` only re-create a PCB if it is already NULL.
- True scope: only the NULL half survives, and only in one state — after `err_tcp` (`api_msg.c:183`) has set `pcb.tcp = NULL`, a subsequent `getsockopt`/`setsockopt` at SOL_SOCKET/IPPROTO_IP level dereferences NULL (no guard, unlike `netconn_peer` at `api_lib.c:219,226` which does check). Real, but a post-error TCP-only crash, not UDP memory corruption. Proposed fix's NULL check is sound; its ENOPROTOOPT-for-non-TCP dispatch is unnecessary for SOL_SOCKET/IP.
