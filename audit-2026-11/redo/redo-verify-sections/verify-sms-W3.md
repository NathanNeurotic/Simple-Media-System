## RE-SMS-061 — WEAKENED
Evidence: `src/SMS_AC3.c:293` `s_LATab[256]` — script-counted: exactly 256 entries, −64…0, non-decreasing (verified). Call sites `:1170` (`case -1: lPSD = lNext + s_LATab[(-lDelta) >> 1];`) and `:1176` (`case 0:`). The index expression is a plain `int` — no mask, no clamp — so *if* `lDelta == -512` were reached in `case -1`, the index would be 256, one past the end. That conditional is where the finding fails:
- The filed derivation — "`lDelta` takes multiples of 128; −512 is an exponent drop of exactly 4 between adjacent bands" — does not survive the exponent producer. All `m_Exp` arrays fed to `_ac3_bit_allocate` (FBW `:2183-2189`, coupling `:2165-2169`, LFE `:2198-2204`) are written by `_ac3_parse_exponents` `:628-703`, whose per-step deltas come from `s_Exp1/s_Exp2/s_Exp3` — script-verified: every entry is in [−2, +2], except three poison entries of 25 per table, and any step landing `anExp > 24` (including via the poison, or a uint8 wrap below 0) makes the parse return 1 and the caller abort the frame before bit allocation. Adjacent bins therefore differ by at most 2 (bins in a group share one `anExp`; group steps are ≤ 2).
- Inside the delta loop, `lPSD` satisfies the invariant `lPSD ≤ 128 * lpExp[last processed bin]`: it starts equal at each band, `case -2..-6` resets it to `lNext`, and `case -1`/`case 0` only ever add a `s_LATab` value ≤ 0. Hence for the next bin `lDelta = 128*lpExp[next] − lPSD ≥ 128*(lpExp[next] − lpExp[prev]) ≥ −256`, so in `case -1` the index `(−lDelta)>>1 ≤ 128`, and in `case 0` it is ≤ 255 by the switch range itself. −512 is unreachable from any freshly parsed (or whole-array reused) exponent sequence.
Residual scope the finding does not argue: `EXP_REUSE` frames reuse the previous array, and if a later frame's `EndMant`/`CplStrtMant` grows into slots a previous, shorter parse never wrote (statically zero), an artificial 4→0 adjacency could in principle appear at that stale boundary. No evidence was produced (by the finding or by me) that such a boundary falls inside a bit-allocation band with `lPSD` sitting exactly on the high value. True scope: **an unclamped index whose only proven bound is the producer's ±2 step — a latent one-element over-read contingent on stale-reuse boundary data, not the demonstrated "drop of 4" mechanism as filed.** The clamp fix is harmless and cheap, but the finding as written overstates reachability.

## RE-SMS-069 — VERIFIED
Evidence: `src/SMS_EE.c:45-53`: `*apSize = 17 * aMinSize / 16 + 32; return realloc(apData, *apSize);` — the size is published *before* the call and is never rolled back, so a NULL return leaves the caller holding NULL + an inflated size, and the old pointer is lost. AVI call sites do exactly the dangerous thing: `src/SMS_ContainerAVI.c:169-176` (`_Load_idx1`) and `:281-288` (`_LoadODMLIdx`) both do `lpIndices = SMS_Realloc(...); lpStm->m_pIdx = lpIndices; lpIndex = &lpIndices[m_nIdx++]; lpIndex->m_fKey = …;` — storing NULL over the old table and writing through `&NULL[m_nIdx]`. The safe in-tree pattern the finding cites is present and even self-documenting: `src/SMS_ContainerMOV.c:919-929` `_add_idx_entry` grows into a *local* `lAllocSize`, tests `if (!lpIndices) return 0;`, publishes pointer + size only on success, and carries the comment "SMS_Realloc grows by 17/16 and publishes its size even if realloc fails." ## RE-SMS-070 — WEAKENED
Evidence: `iop/SMSMAP/smap.c:886-921` `SMap_Send`: chained-pbuf arm gathers the whole chain with `mips_memcpy` per link into `static u32 sl_TXBuf[(SMAP_TXMAXSIZE + SMAP_TXMAXTAILPAD + 3) / 4]`; the only length gate is `if (lTXLen > lpSMap->m_TXFree) return SMap_TX;` with `m_TXFree = 4096` (`smap.c:708`, `main.c:165`). So the bound mismatch is real in code: the gate admits chains up to 4096 bytes into a 1520-byte buffer.
Why not VERIFIED: the finding is titled INFERRED and its own text concedes normal traffic cannot produce such a chain — and my caller check agrees: everything reaching `linkoutput` in this stack is a single Ethernet frame (≤ 1500 MTU + 14 header = 1514, exactly `SMAP_TXMAXSIZE`), and `ip_output_if` fragments anything larger before the driver. No in-tree path was found (by the finding or by me) that hands `SMap_Send` a chain with `tot_len` in (1520, 4096]. True scope: **a wrong-constant latent bound — the gather is incidentally safe today because of the MTU, not because of its gate — not a demonstrated overflow.** It does not present the inference as fact (title and confidence both say INFERRED), and the one-constant fix is sound hardening; it stands only in that weakened form.

## RE-SMS-072 — VERIFIED
Evidence: `iop/SMSTCPIP/src/api_msg.c:505-525` `do_connect`. UDP arm `:512-514` (all three UDP cases): `udp_connect(...)` return discarded, `conn->err` untouched, then `sys_mbox_post(conn->mbox, NULL)` unconditionally — so a failed `udp_connect` (its bind-failure return is real: `udp.c:662-670` returns `udp_bind`'s error) is reported to the caller as success, exactly as filed. TCP arm `:517-519`: `setup_tcp(msg->conn); tcp_connect(...)` — return discarded, no `sys_mbox_post` in the arm, `conn->err` never set from it. `tcp_connect` (`tcp.c:489-540`) returns `tcp_enqueue`'s result, which can fail synchronously (e.g. ERR_MEM). The caller `netconn_connect` (`api_lib.c:287-316`) blocks in `sys_mbox_fetch(conn->mbox, &mem)` and returns `conn->err`; on the TCP success path the only post is inside `do_connected`, which fires on SYN-ACK. So a synchronous TCP failure leaves the caller waiting until the SYN retransmission machinery aborts the PCB and `err_tcp` happens to post the mbox — the finding's "hangs / duration INFERRED" framing is accurate, including its hedge. Fix (capture the return in both arms, post only on synchronous error) correctly avoids double-posting the async success path.
